## Ограничения и шаги владельца

Rollback компенсирует только незавершённый запрос с полным поддерживаемым журналом. Он не отменяет любую завершённую историю и не разрешает автоматически конфликтующие финансовые правки. Все ссылки на отсутствующие месячные снимки сохраняются с предупреждением; снимки не восстанавливаются.

После тестового выпуска нужно подтвердить живое применение: переименование категории и её заголовка в сводном «Архиве», возврат нужной неактивной категории со всеми текущими подкатегориями и новая операция. Контролируемый частичный сбой/пользовательский rollback следует проверять на согласованном запросе, без случайных синтетических категорий, финансовых строк или вмешательства в чужие pending. Перед/после сравнить суммы, UUID, архивную колонку, chart metadata и ready/open.

## Ручная приёмка и исправления по её результатам

Владелец подтвердил отмену восстановления, восстановление категорий/подкатегорий, корректные исторические значения и работу отката. Переименование и первая запись после восстановления приёмку не прошли; общие временные ошибки Google отдельно не классифицировались старой диагностикой.

Подтверждённые причины:

1. Запрос `100cc8d7-b823-4d0c-8b9f-e9e3351ce17d` требовал строку 441 в `_financebot_archive_labels`, фактически выделено 437 строк. Это прочитано из серверного журнала и gridProperties ИФТ без записи. Новый precision writer не расширял сетку до целевого диапазона. Добавлен журналируемый capacity-шаг до чтения/записи нового диапазона; resume после потерянного ответа не добавляет строки дважды, rollback не удаляет расширенные строки и чужие данные. Регрессия воспроизводит именно границу 437→441 со строгим fake API.
2. Код `103e888` воспроизвёл ложный конфликт «Таблица изменилась перед записью»: `_ledger` записывал собственные служебные ID и возвращал старый raw, с которым append затем сравнивал обновлённую книгу. Новая сверка возвращает состояние после собственных записей; реальная сторонняя правка по-прежнему блокирует добавление. Проверены успешное первое добавление после ручной строки и отсутствие дубля.

Для снижения запросов объединены чтения источника/снимков/meta; повторное полное чтение registry заменено проверкой scope/revision в metadata. Неизменённые служебные значения повторно не записываются. Native apply использует один свежий исходный снимок вместо трёх одинаковых полных чтений до первой записи, а финальная готовность читается только из metadata. Gates source fingerprint, before/after, финансовых полей и revision сохранены.

Ошибки теперь содержат HTTP-код и тип исключения, а безопасная история ошибок сохраняется даже после успешного отката. До отправки финансового batch и при явном отказе Google пользователь получает сообщение об отсутствии финансовой записи; неопределённый сетевой результат после отправки по-прежнему не повторяется автоматически. INFO-логирование HTTP URL Telegram отключено, так как URL содержит токен.

Гипотеза о quota для общих временных отказов пока не доказана HTTP 429 из прежних логов; код прежней версии скрывал статус. Стандартные лимиты и общий service account означают, что нагрузка ИФТ и прома может суммироваться. Это не причина двух воспроизведённых дефектов выше. Новая безопасная диагностика позволит отличить 429 от остальных отказов без публикации API bodies.

Повторный прогон после этих исправлений: 215 Python-тестов прошли, все три Node-сценария прошли, strict OpenSpec 15/15 и diff --check без ошибок. Живое применение новых исправлений ещё требует ретеста переименования и первой записи; ранее принятые владельцем восстановление и откат не объявляются заново непроверенными.
