# ADR-001: Отдельный тестовый бот и ветка разработки

Статус: принято владельцем и реализовано; подробности [в карте окружений](../09-environments-and-branches.md). Дата фиксации: 2026-11-12.

## Контекст

Разработка динамических категорий меняет контракт таблицы, Apps Script и Telegram UI одновременно. Пробный выпуск на исходного бота приводил к блокировкам несовместимых привязок, затем был отменён откатом на стабильную версию. Доступность контейнера и успешный deploy оказались недостаточным свидетельством работоспособности пользовательских сценариев. Владелец создал второй бот и согласовал отдельный стенд; затем попросил разделить ветки.

## Решение

- `main` хранит стабильный рабочий вариант; `feature/manage-categories` — разрабатываемый v2-код и контекст.
- Рабочий и тестовый боты имеют разные Telegram token/bot ID, spreadsheet_id, контейнеры, Compose project, env и каталоги журналов.
- Тестовый стенд использует отдельную уже выделенную v2-копию. Согласие на тестовый сценарий не разрешает менять рабочие финансовые данные.
- Рабочий workflow запускается тегами `v*`, тестовый — `test-*`. Передеплои выполняются существующим GitHub Actions, без запуска второго polling на рабочем токене.
- Изменения сначала проверяются на тестовом боте. Перенос в production требует отдельной приёмки, проверки production-конфигурации, а для v2 — миграции рабочей книги и согласования Apps Script.
- Дополнительные аккаунты временно выключены по решению владельца; их исходные привязки сохраняются для контролируемого возврата.

## Почему так

Один бот и одна таблица для разработки и личных финансов делают экспериментальный контракт частью рабочего процесса. Две ветки без отдельных token и spreadsheet_id не изолируют процессы и данные. Отдельные token, книга и контейнер позволяют тестировать изменения, сохраняя стабильный рабочий вариант.

Постоянная ветка `test` не нужна для текущего процесса: стенд получает выбранный коммит feature через тег. Имя ветки не заменяет идентификацию развернутого коммита.

## Рассмотренные варианты

- Сохранять новую разработку в main и держать рабочий бот на старом теге: использовалось временно, но скрывало различие между main и реальным production; заменено стабильным main и feature-веткой.
- Проверять v2 на исходном боте с возможностью отката: использовалось до создания стенда; теперь для новых проверок выбран отдельный бот.
- Постоянная ветка test: обсуждалась как необязательная; выбрана feature-ветка и версионированный test deploy.

## Последствия и ограничения

- Оба окружения разделяют сервер, deploy-аккаунт и Google service account. Это не полноценная изоляция инфраструктурных прав.
- Bound Apps Script устанавливается отдельно от Docker-образа. Для каждой книги важны собственный исходник, триггеры и schema scope.
- Общей репликации между книгами нет. Merge переносит код, но не тестовые операции и не ID реестров в рабочую книгу.
- В feature остался production Compose от предыдущей попытки с test spreadsheet_id; это известный пункт проверки перед merge, не новая рабочая привязка.
- Продвижение единого Docker digest между test и production не реализовано. Текущая приёмка относится к конкретному test-коммиту и набору сценариев; повторная сборка не объявляется побитово тем же образом.
- Полная приёмка UI управления категориями остаётся открытой. Подтверждено владельцем, что оба бота работают и отвечают после последних передеплоев.
