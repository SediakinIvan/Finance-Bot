# Инженерные стандарты

## Основание

Базовые правила ниже сформулированы по запросу владельца в ходе интервью; это новые стандарты для изменений, а не утверждение о соответствии всего существующего кода.

## Правила для изменений

- Следовать [PEP 8](https://peps.python.org/pep-0008/): понятные английские имена, `snake_case` для функций и переменных, `PascalCase` для классов, `UPPER_CASE` для констант. В новых модулях использовать отступ в 4 пробела; в существующих сохранять локальную согласованность без смешивания табов и пробелов.
- Разделять импорты стандартной библиотеки, внешних пакетов и проекта. Не выполнять массовое переформатирование вместе с функциональной правкой — это затрудняет ревью.
- Добавлять аннотации типов для новых и изменяемых интерфейсов. Комментарии объясняют причины и ограничения; docstring описывает неочевидный контракт.
- Проверять внешние данные на входе; обрабатывать конкретные ожидаемые исключения. Не скрывать ошибки пустым `except` и не выдавать неуспешную операцию за успешную.
- Делать изменения небольшими и связанными с задачей. При изменении поведения обновлять документацию и проверять затронутые сценарии; исправления ошибок сопровождать содержательными регрессионными тестами.
- В автоматических тестах подменять Telegram и Google Sheets; не использовать реальные финансовые данные, ключи и рабочую таблицу.

## Подтверждённые настройки проекта

- Среда контейнера: Python 3.12 (`Dockerfile`). Зависимости: `requirements.txt`.
- Инструкции запуска и проверки: `README.md`; автоматизация: `.github/workflows/ci-cd.yml`.
- Локальная команда тестов из README: `python -m unittest discover -s tests`.
- Команда тестов в CI: `python -m unittest discover -s tests -v`. Все тесты должны проходить без ошибок и падений.
- Перед живой проверкой README требует использовать копию таблицы.
- Отдельные конфигурации линтера, форматтера и проверки типов при осмотре не обнаружены; не считать эти проверки настроенными. В ходе интервью тесты не запускались.
