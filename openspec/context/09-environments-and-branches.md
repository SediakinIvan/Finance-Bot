## Границы изоляции

- Два токена, два spreadsheet_id, два контейнера, два Compose project и раздельные журналы. Одного токена на два polling-процесса быть не должно.
- Сервер, deploy-аккаунт, SSH/registry-секреты и Google service account общие. Это логическая изоляция окружений, а не отдельные серверы или раздельные Google-права.
- Ключ Google монтируется RO из общего `secrets/google-service-account.json`. Тестовый env не получает рабочий токен; подготовка сравнивает ID ботов и отклоняет совпадение.
- Рабочий `.env` при подготовке тестового не переписывается. В нём остаются исходные настройки и дополнительные привязки; эффективное значение `GOOGLE_SHEET_ID` рабочего бота берётся из `main:compose.yaml`.
- Между таблицами нет репликации. Тестовые категории, операции, архивы и ID автоматически в рабочую таблицу не переносятся.
- Таблицы с ID `1_Zeo-E_fNjPoI0TXJWbm8wrMpldKNbeL_qb8PyKfmA8`, `148_gG5DbHos4-UbF0lDpQUlRWxH1Rh85ZFaJp0cHkDE`, `1eHAJojgqUe-3Ia_d7CZbMzsexIxi9proaEa9HXmWFEg` не являются текущими основными привязками этих двух окружений. Первая встречалась как дополнительная привязка; предыдущая идентификация её как основной была ошибочной. Остальные использовались в прошлых проверках/как копии; не переключать на них бот по старым заметкам.

## Работа с ветками

`main` содержит стабильный производственный вариант. `feature/manage-categories` содержит всю новую разработку и этот контекст. Разделение выполнено без переписывания удалённой истории: коммит `77c4d22` вернул стабильное дерево в main, `d85803a` сохранил развитие поверх этой основы. Поэтому ветку можно впоследствии слить обычным merge; тестовые теги и история не потеряны.

На момент разделения в стабильном `main` нет `openspec/`, `docs/`, `compose.test.yaml` и workflow тестового стенда: они добавлены разработкой и пока находятся в feature. Отсутствие этих файлов в main не означает отсутствие OpenSpec в проекте в целом; для работы с контекстом использовать feature. Не запускать `openspec init` в main ради восстановления контекста.

Постоянная ветка `test` не создана. Стенд получает выбранный коммит feature через тег `test-*`. Push feature сам по себе не разворачивает бота. Push main запускает CI/публикацию образа, но без рабочего тега не выполняет deploy.

## Критичное отличие конфигураций перед merge

`feature/manage-categories:compose.yaml` унаследован от попыток v2-выпуска и указывает на тестовую таблицу `1jaEzm…`. Это **не актуальная рабочая конфигурация**. Реальный тестовый стенд использует `compose.test.yaml` и `scripts/prepare_test_env.py`, а реальное рабочее окружение — `main:compose.yaml` с `1I6_HFC…`.

Нельзя просто слить feature и выпустить рабочий тег: потребуется отдельно подготовить миграцию рабочей таблицы к v2, проверить её Apps Script, восстановить правильный production spreadsheet_id в Compose, сохранить отдельный тестовый workflow и согласовать выпуск. Нельзя переносить тестовый токен, данные или синтетические категории в рабочее окружение как побочный эффект merge.

Автоматическое продвижение уже проверенного test-образа в production пока **не реализовано**: два workflow собирают образы отдельно. Это желаемое развитие процесса, не существующая гарантия.
