# Purpose

Фиксировать действующее разделение стабильного рабочего бота и экспериментального тестового стенда, предотвращать смешение токенов, таблиц, веток и журналов. Конкретные ID, версии и свидетельства последних выпусков находятся в [карте окружений](../../context/09-environments-and-branches.md); различия хранилищ — в [контракте версий таблиц](../workbook-versions/spec.md).

Эта спецификация документирует текущие договорённости и реализацию. Требования к будущему переносу ниже являются условиями следующего выпуска, а не утверждением, что рабочая миграция или автоматическое продвижение образа уже реализованы.

## Requirements

### Requirement: Стабильная и разрабатываемая ветки
Рабочий код SHALL выпускаться из принятого состояния `main`. Незавершённое управление категориями SHALL сохраняться в `feature/manage-categories` и проверяться на тестовом стенде. Имя окружения SHALL не вычисляться из одного лишь имени текущей локальной ветки: выпуск идентифицируется коммитом и тегом.

#### Scenario: Локальный checkout
- **WHEN** разработчик переключает локальную ветку
- **THEN** существующие контейнеры не меняются без отдельной раскатки; состояние рабочего бота определяется последним успешным deploy.

#### Scenario: Разделение истории
- **WHEN** стабильная основа выделяется из уже опубликованного main
- **THEN** разработка и теги сохраняются, возврат main фиксируется обычным коммитом, а feature остаётся пригодной для последующего merge без force-push.

### Requirement: Две явные таблицы
Рабочее окружение MUST использовать только согласованную рабочую таблицу `1I6_HFCMVmxOD5buP6RdhtfJHld66tj7oMGArpW4AEC4`, тестовое — только выделенную v2-копию `1jaEzmJPqYzxSp-HtDw-zwt_kPqSEs4enBrkG-Lc-UzA`. Смена привязки SHALL быть отдельным решением владельца. Неудача доступа MUST не вызывать автоматического переключения на другую копию.

#### Scenario: Таблица из старой заметки
- **WHEN** в старом журнале обнаружен другой spreadsheet_id
- **THEN** он не подставляется в конфигурацию вместо действующей карты окружений.

#### Scenario: Поломка теста
- **WHEN** тестовая таблица содержит ошибку, экспериментальные категории или незавершённую операцию
- **THEN** исправление ограничивается тестовой областью; рабочие данные не восстанавливаются из теста и не очищаются.

### Requirement: Независимые Telegram-токены
Тестовый бот MUST иметь отдельный token и bot ID. Подготовка его конфигурации MUST отклонять токен с тем же ID бота, что у рабочего, в том числе после ротации токена. На один token SHALL работать не более одного polling-процесса.

#### Scenario: Совпадение бота
- **WHEN** `TEST_TELEGRAM_BOT_TOKEN` принадлежит рабочему bot ID
- **THEN** генерация тестового env завершается ошибкой до запуска контейнера.

#### Scenario: Хранение секрета
- **WHEN** тестовый стенд готовится через GitHub Actions
- **THEN** token поступает из `TEST_TELEGRAM_BOT_TOKEN` через stdin, записывается в приватный `.env.test` и не включается в Git, аргументы команд или обычные сообщения.

### Requirement: Изоляция процессов и постоянного состояния
Тест SHALL запускаться с Compose project `financebot-test`, контейнером `financebot-test`, каталогом `<VPS_APP_DIR>/test`, собственным env и журналом. Рабочая раскатка SHALL использовать свой корневой каталог и контейнер `financebot`. Команды test SHALL не заменять рабочие Compose/env и не удалять рабочий контейнер как orphan.

#### Scenario: Передеплой теста
- **WHEN** выполняется test deploy с `--remove-orphans`
- **THEN** область операции ограничена project `financebot-test`, рабочий контейнер не пересоздаётся.

#### Scenario: Рестарт
- **WHEN** тестовый контейнер заменён или перезапущен
- **THEN** его приватные планы остаются в `test/secrets/category-changes`; рабочий каталог журнала не используется как источник восстановления.

### Requirement: Явная эффективная конфигурация
Значения Compose `environment` SHALL учитываться как переопределения `env_file`. Рабочий `GOOGLE_SHEET_ID` SHALL определяться стабильным `main:compose.yaml`; тестовые настройки SHALL готовиться `scripts/prepare_test_env.py` и читаться через `compose.test.yaml`. Локальный `.env` разработчика SHALL не считаться свидетельством настроек работающего контейнера.

#### Scenario: Дополнительные пользователи
- **WHEN** запускается любое из текущих окружений
- **THEN** дополнительные аккаунты отключены; исходные привязки могут оставаться в рабочем серверном `.env`, но не являются эффективными настройками контейнеров.

#### Scenario: Возврат дополнительного аккаунта
- **WHEN** владелец решает вернуть доступ
- **THEN** его таблица проверяется на совместимость с адаптером выбранного окружения до включения привязки; пользователь не перенаправляется в таблицу другого владельца.

### Requirement: Раздельные триггеры и образы
Теги `v*` SHALL запускать рабочий workflow `CI/CD`; теги `test-*` — workflow `Test stand`. Test SHALL публиковать только `test-<commit>` и не перезаписывать рабочий `latest`. Push обычной feature SHALL не выполнять deploy. Push main без рабочего тега SHALL не выполнять production deploy.

#### Scenario: Рабочий релиз
- **WHEN** отправлен согласованный тег `v*` из main и включён `ENABLE_VPS_DEPLOY`
- **THEN** рабочий workflow выполняет тесты, сборку и раскатку стабильной конфигурации.

#### Scenario: Тестовый релиз
- **WHEN** отправлен тег `test-*`, указывающий на feature-коммит
- **THEN** его workflow проверяет Python/Apps Script, собирает тестовый образ и обновляет только тестовый project.

#### Scenario: Ручной запуск после разделения веток
- **WHEN** `Test stand` отсутствует в default branch main
- **THEN** доступность `workflow_dispatch` через интерфейс GitHub не предполагается; действующий способ запуска — test-тег на коммите, содержащем workflow.

### Requirement: Совместимость проверяется до замены
Test deploy MUST проверить доступность постоянного журнала и для каждой включённой таблицы вызвать чтение каталога, статуса изменения и вариантов новых операций. Требуются корректный scope, schema=2 и ready/open без несовместимого pending. Несовместимая дополнительная таблица MUST не игнорироваться молча.

#### Scenario: Проверка не пройдена
- **WHEN** таблица не соответствует v2, недоступна Google либо журнал недоступен
- **THEN** test deploy завершается ошибкой до замены контейнера и выдаёт диагностируемый этап без токенов и финансового содержимого.

#### Scenario: Успешный deploy
- **WHEN** все этапы пайплайна завершились успешно
- **THEN** подтверждено выполнение автоматических проверок и команд раскатки; полная приёмка Telegram-диалогов не объявляется автоматически выполненной.

### Requirement: Доказательная приёмка
Каждый отчёт о выпуске SHALL указывать окружение, branch, commit/tag, spreadsheet_id и результат workflow. Проверка владельцем SHALL отдельно покрывать ответы в Telegram; для v2 — также жизненный цикл категорий и историю. Неопределённый результат SHALL оставаться открытым пунктом, а не считаться успехом.

#### Scenario: Проверка без финансовой записи
- **WHEN** проверяется доступность после передеплоя
- **THEN** сначала проверяются `/version`, справка, аналитика и последние операции; новая расходная запись не создаётся без намерения и подтверждения пользователя.

#### Scenario: Приёмка управления категориями
- **WHEN** принимается v2 UI
- **THEN** на тесте проверяются create, cancel/repeat, rename, move, deactivate, доступность нового варианта, суммы и индексированные архивные подписи; общий ответ «бот заработал» не закрывает все эти сценарии.

### Requirement: Контролируемый перенос в production
Merge feature SHALL не переносить тестовые данные, token и привязку таблицы в рабочее окружение. Перед рабочим v2-релизом MUST отдельно согласовать миграцию рабочей книги, backup, актуальный Apps Script, production-конфигурацию и приёмку. Унаследованный `feature:compose.yaml` с тестовым ID MUST быть исправлен до рабочего выпуска.

#### Scenario: Выпуск без миграции
- **WHEN** v2-код предлагается подключить к legacy-таблице
- **THEN** выпуск останавливается; смена одного spreadsheet_id не заменяет миграцию.

#### Scenario: Синтетические данные
- **WHEN** на тесте созданы тестовые категории и операции
- **THEN** они не копируются в рабочую таблицу при merge или создании release tag.

### Requirement: Откат учитывает контракт данных
Откат SHALL выбирать совместимые код, конфигурацию таблицы и Apps Script. После появления v2-операций SHALL не выполняться простой запуск v1-адаптера на той же мигрированной книге. Данные и журнал MUST сохраняться до решения владельца о восстановлении.

#### Scenario: Откат к отдельной legacy-книге
- **WHEN** возвращается стабильный v1-код и его прежняя рабочая привязка
- **THEN** v2-тестовая книга не очищается и не объявляется автоматически синхронизированной с рабочей.

## Фактические ограничения

- Сервер, deploy-аккаунт, Google service account и часть GitHub secrets общие. Совпадение аккаунта доступа не разрешает писать в чужую область.
- Оба job используют GitHub environment `production` для существующих SSH/registry credentials; test-target определяется командами и Compose project, не названием этого environment.
- Рабочий стабильный workflow не содержит v2 release_check. Его успешная раскатка не доказывает совместимость с произвольной другой книгой.
- Автоматическое продвижение одного и того же проверенного Docker digest из test в production не реализовано: текущие workflow собирают отдельно. Нельзя обещать побитовую идентичность образов после повторной сборки.
- GitHub Actions не устанавливает bound Apps Script и не включает onEdit в книге автоматически.

- Условие рабочего deploy в существующем CI/CD проверяет `v*`, событие и ENABLE_VPS_DEPLOY, но **не проверяет принадлежность тега main**. Выпуск только из принятого main — договорённость процесса; перед созданием тега оператор обязан проверить его целевой коммит. Автоматический ancestry gate пока не реализован.
- Рабочая сборка публикует теги commit, ref_name и latest. Поэтому имя образа commit/latest само по себе не является доказательством окружения или неизменности digest; отчёт о выпуске должен сохранять конкретный проверенный commit/tag. Тестовая сборка использует отдельный префикс test-.
