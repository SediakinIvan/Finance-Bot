# Purpose

Разделить legacy-контракт рабочей таблицы и v2-контракт тестовой. Одинаковые видимые листы и названия кнопок не означают одинаковую модель данных. Источники: `main` и `feature/manage-categories`, миграционные артефакты, согласованные владельцем правила и результаты тестов. Это описание программных контрактов; оно не является свежей побайтовой инвентаризацией двух живых книг.

Привязки и развёрнутые версии: [карта окружений](../../context/09-environments-and-branches.md). Рабочая книга не мигрировалась к v2 в рамках последних выпусков. V2-копия развивается независимо; одинаковые суммы, периоды, категории и операции между книгами не предполагаются.

## Сравнение контрактов

| Область | Рабочая legacy/v1, ветка main | Тестовая v2, ветка feature/manage-categories |
| --- | --- | --- |
| Доступ из Python | `GoogleSheetsStore` | `V2GoogleSheetsStore` поверх общего клиента |
| Основные видимые листы | «Траты», «Категории», «Аналитика», «Архив», месячные снимки | Те же назначения, плюс служебная модель v2 |
| Пользовательская операция | A:F: дата, категория, подкатегория, сумма, тип, примечание | A:F сохранены; G:K содержат пять служебных полей |
| Идентичность категории | Текстовое название и тип | Постоянный category_id, отображаемое имя, active, период деактивации |
| Идентичность подкатегории | Название в категории | Постоянный subcategory_id и current_category_id |
| Исторический родитель | Отдельного ID операции и реестра старых пар нет | В операции собственный category_id; прежние пары сохраняются отдельно |
| Идентичность операции | Физическая строка и снимок A:F при удалении | transaction_id, снимок связей, физическая строка и проверка её значений |
| «Категории» A:C | Источник вариантов ввода; Тип / Категория / Подкатегория | Генерируемый вид активных пар, а не источник истины |
| Доходы | Адаптер нормализует категорию в «Доход» | Сохраняются отдельные категории дохода; бот предлагает выбор, если их несколько |
| Новая строка из бота | Первая пустая дата в A, даже если B:F заполнены | Полностью свободная пользовательская строка; частичный ввод не перезаписывается как пустой |
| Даты | Бот записывает текст ДД.ММ.ГГГГ с RAW | Видимая дата сохраняется, числовая report_date в K используется для расчёта |
| Готовность данных | Обязательных meta/schema gates нет | Scope, schema=2, revision, ready/open и отсутствие pending |
| Ручной ввод | Зависит от существующих формул и валидаций книги | onEdit/полная сверка обновляют ID, снимки и validation_state |
| Побочные записи при чтении | Чтение последних операций/аналитики само не ведёт v2-снимки | Эти действия проходят `_ledger` и могут записывать G:K и служебные снимки |
| Месячная аналитика | Чтение рассчитанных подписанных блоков | Перед отчётом сверка строк и F1=ready; расчёт по сохранённым ID/датам |
| Детализация в боте | Четыре фиксированные категории | Динамические страницы по восемь, callback по category_id |
| Управление категориями | Кнопки нет | `/categories`, создание, переименование, перенос и деактивация с подтверждением |
| Макрос из Git | Фиксированные B9:B22, 14 расходных категорий | Реестры, независимая сверка итогов, стабильный индекс архивных колонок |
| Снимок месяца | Значения «Аналитики», не исходные операции | Читаемый dashboard со значениями и диаграммами, ID в отдельном индексе |
| Защита очистки в макросе | Legacy-исходник не содержит отдельного подтверждения очистки | Отдельное подтверждение, проверки периода и неизменности данных |
| Восстановление изменения категорий | Сервиса нет | Maintenance/pending и точный приватный план с request_id |
| Предел изоляции | Свой spreadsheet_id | Свой spreadsheet_id и журналы, не общий реестр с рабочей книгой |

Legacy здесь — имя программного контракта. В рабочей книге не предполагается наличие ячейки `schema_version=1`: обязательные метаданные появляются только в v2.

## Структура v2 по листам

### Пользовательская операция «Траты»

| Колонка | Заголовок | Значение / правило |
| --- | --- | --- |
| A | Дата | Видимая дата операции |
| B | Категория | Читаемая подпись категории |
| C | Подкатегория | Читаемая подпись подкатегории |
| D | Сумма | Положительная конечная сумма; ввод бота по-прежнему в целых рублях |
| E | Доход/Расход | Поддержанные типы «Доход» и «Расход» |
| F | Примечание | Пользовательский текст |
| G | category_id | Историческая категория именно этой операции |
| H | subcategory_id | Постоянная подкатегория |
| I | transaction_id | UUID операции; не копировать в новую строку |
| J | validation_state | valid либо диагностическое состояние; пусто у пустой строки |
| K | report_date | Числовая дата Sheets для формул |

G:K могут быть скрыты, но являются частью строки. Перестановка или сортировка только A:F нарушает идентичность; переносить строку целиком A:K. Нельзя «чинить» J вручную на valid без сверки. Числовая дата, Date Sheets и текст ДД.ММ.ГГГГ / YYYY-MM-DD нормализуются; недопустимая дата не превращается в нулевую сумму.

### Служебные листы

| Лист | Заголовки / ключи | Назначение |
| --- | --- | --- |
| `_financebot_meta` | key, value | spreadsheet_id, schema_version, taxonomy_revision, migration_state, access_mode, pending_request_id |
| `_financebot_categories` | category_id, type, name, active, deactivated_period | Категории, включая неактивные |
| `_financebot_subcategories` | subcategory_id, current_category_id, name, active | Текущий родитель и активность подкатегории |
| `_financebot_category_history` | category_id, subcategory_id | Допустимые исторические пары |
| `_financebot_row_snapshots` | transaction_id, category_id, subcategory_id, category_label, subcategory_label, transaction_type | Доверенные связи до ручной правки |
| `_financebot_detail` | category_id, subcategory_id, category, subcategory, amount | Детализация по историческим парам выбранного периода |
| `_financebot_archive_columns` | category_id, column | Неизменное соответствие категории и колонки сводного архива |
| `_financebot_archive_labels` | sheet, cell, kind, category_id, subcategory_id | Адреса индексированных подписей аналитики и старых снимков |

Служебные листы могут быть скрыты/защищены оформлением миграции. Скрытие не является разграничением доступа. Произвольное ручное изменение UUID, метаданных и индексов не поддерживается. Восстановление исходных удалённых операций из агрегированного архива не гарантируется ни одной версией.

## Сверка при чтении

Сверка `_ledger` используется также перед добавлением, просмотром последних операций и удалением. Поэтому незавершённая ручная строка может временно блокировать эти действия, а не только месячную аналитику. Обновление служебных G:K и `_financebot_row_snapshots` возможно даже при команде просмотра; пользовательские A:F этим этапом не переписываются. Тестовый release_check использует каталог, статус и варианты ввода, а не эти методы с побочной записью.

## Requirements

### Requirement: Контракт выбирается по окружению
Клиент MUST работать с явно выбранной книгой и совместимым адаптером. V2 MUST не переходить автоматически на текстовый legacy-реестр при отсутствии служебных листов. Совпадение видимых A:F MUST не трактоваться как завершённая миграция.

#### Scenario: Скопированная v2-книга
- **WHEN** книга скопирована и получила новый spreadsheet_id
- **THEN** прежние метаданные scope не принимаются как корректные для нового ID; требуется явная подготовка и проверка новой области.

### Requirement: Источник истины справочника
В legacy варианты SHALL читаться из A:C «Категории». В v2 источником истины MUST быть служебные реестры и revision; вид «Категории» SHALL генерироваться из активных пар. Правка представления вне сервиса SHALL приводить к ошибке согласованности, а не к молчаливому изменению реестра.

#### Scenario: Название изменили вручную в «Категории»
- **WHEN** представление v2 расходится с реестром
- **THEN** бот требует восстановления согласованности; изменение не считается глобальным переименованием.

### Requirement: Имена и постоянные ID
V2 SHALL сохранять UUID при переименовании. Имена категорий SHALL быть уникальны после нормализации внутри типа, подкатегорий — внутри текущего родителя, включая неактивные сущности. Одинаковые названия в разных допустимых контекстах SHALL не объединять их ID.

#### Scenario: Переименование исторической сущности
- **WHEN** подтверждено новое имя активной или неактивной сущности
- **THEN** меняются связанные подписи операций, отчётов и индексированных архивов, но не суммы, UUID и историческая принадлежность операции.

### Requirement: Перенос для новых операций
V2 MUST сохранять прежний category_id существующих операций при переносе подкатегории. Перенос SHALL быть разрешён только между активными категориями одного типа без конфликта имени.

#### Scenario: Старая и новая траты
- **WHEN** использованная подкатегория перенесена из A в B
- **THEN** старая трата остаётся в A, новая выбирает B; неизменный subcategory_id связывает их с одной подкатегорией.

### Requirement: Удаление означает деактивацию
V2 MUST исключать неактивную сущность из новых вариантов без удаления исторических операций и архивных колонок. Категория MUST хранить период деактивации YYYY-MM.

#### Scenario: Архив после деактивации
- **WHEN** закрывается период деактивации категории
- **THEN** её колонка содержит фактическую сумму этого периода; за более поздние периоды — нули, прежние архивные суммы сохраняются.

### Requirement: Сверка ручных строк
V2 MUST сверять пользовательские A:F с текущими реестрами и доверенными снимками, обновлять служебные поля и обнаруживать дубли/подмену ID. Несовместимые или незавершённые строки SHALL блокировать полный отчёт и архивацию вместо выдачи неполных итогов.

#### Scenario: Частично введённая строка
- **WHEN** дата пуста, но другие пользовательские ячейки заполнены
- **THEN** v2 не использует строку для новой траты и не перезаписывает её A:F как свободные.

#### Scenario: Историческая пара
- **WHEN** старая операция с неактивной или перенесённой подкатегорией имеет доверенный снимок
- **THEN** её историческая пара сохраняется; произвольно вставленные UUID сами по себе такого права не дают.

### Requirement: API и onEdit
V2-бот MUST сам записывать служебные поля для своих операций; изменения через API SHALL не полагаться на автоматический запуск onEdit. Обновление справочника SHALL обновлять зависимые списки ручного ввода до публикации ready. Связанный Apps Script SHALL обеспечивать onEdit и полную сверку ручного ввода в самой книге.

#### Scenario: Добавили подкатегорию через бота
- **WHEN** подтверждённое изменение завершено
- **THEN** новый вариант появляется в боте и соответствующих validation rules Sheets без ручного редактирования макроса и без ожидания onEdit от API.

#### Scenario: Сбой ручного триггера
- **WHEN** ручная строка не получила служебные поля
- **THEN** владелец проверяет bound Apps Script и при необходимости запускает refreshFinanceBotRows; не переносит служебные ID из соседней траты.

### Requirement: Аналитика по идентичности
V2 SHALL считать выбранный период по report_date и сохранённой паре category_id/subcategory_id. Перед выдачей отчёта SHALL выполняться сверка строк и проверка ready. Суммы категорий/подкатегорий SHALL не смешиваться только из-за совпадения названий.

#### Scenario: Две одноимённые подкатегории
- **WHEN** разные категории содержат одинаковое название подкатегории
- **THEN** их ID и аналитика остаются раздельными.

#### Scenario: Месяц в таблице
- **WHEN** запрошена аналитика любого окружения
- **THEN** читается выбранный в D1/D2 период; календарный месяц запроса сам по себе его не переключает.

### Requirement: Динамический dashboard и архив
V2 SHALL генерировать категории A9:D и детализацию по реестру, сохранять читаемые блоки/диаграммы и связывать архивные колонки через ID. Новые категории SHALL не требовать ручного добавления фиксированной переменной в архиватор.

#### Scenario: Новый месячный снимок
- **WHEN** создаётся архив аналитики
- **THEN** замораживаются значения и читаемое оформление; служебные category_id/subcategory_id не накладываются на видимые блоки и не сдвигают их. Индексы подписей хранятся отдельно.

### Requirement: Подтверждения архивации
V2-архиватор MUST проверить строки, период, согласованность итогов и неизменность данных после пользовательских диалогов. Замена существующего архива и очистка «Трат» SHALL требовать подтверждения. Данные других периодов SHALL не очищаться как траты закрываемого месяца.

#### Scenario: Отказ от очистки
- **WHEN** пользователь отклоняет очистку
- **THEN** исходные операции остаются; сохранённый архив не означает согласия на удаление.

#### Scenario: Частичный сбой архива
- **WHEN** архивирование уже изменило архив и завершилось ошибкой
- **THEN** обслуживание сохраняется для проверки; нельзя вручную объявлять open без восстановления согласованности.

### Requirement: Приватный подтверждённый план
Изменение справочника в v2 MUST иметь owner/scope, revision, source fingerprint и request_id. Предпросмотр SHALL не писать в Sheets. Устаревший источник или период SHALL требовать нового подтверждения. Частичное применение SHALL продолжаться по сохранённому плану, а не создавать новую сущность.

#### Scenario: Подтверждение после новой траты
- **WHEN** после предпросмотра изменились исходные данные
- **THEN** старый план отклоняется без автоматического перепланирования и применения.

#### Scenario: Журнал потерян
- **WHEN** у pending-запроса отсутствует или повреждён точный журнал
- **THEN** изменение блокируется до восстановления оператором; новый UUID не подменяет незавершённую операцию.

## Отличия интерфейса бота

Legacy имеет десять кнопок в пяти рядах и сворачиваемое reply-меню. V2 сохраняет эти кнопки и добавляет шестой ряд «Категории», `/categories`, фильтр активности, страницы по восемь и выбор сущности по UUID. Новая категория создаётся через тип → имя → 1–20 подкатегорий строками → подтверждение; имя ограничено 1–64 символами с нормализацией пробелов. Доступны добавление подкатегории, rename, move и deactivate. Реактивация и смена типа существующей категории не реализованы.

В обоих окружениях запись и удаление финансовой операции требуют подтверждения. «Выбрать для удаления» показывает последние десять операций, а не полный редактор всей истории. Удаление операции физически удаляет строку; оно не равно кнопке удаления категории, которая в v2 означает деактивацию. Полного Telegram-редактора произвольной старой траты пока нет. Последние операции показываются по порядку строк листа, не путём сортировки по календарной дате.

## Согласованность и ограничения конкурентного доступа

V2-адаптер использует RLock своего store, повторное чтение источника, revision и fingerprint. Apps Script использует document lock и перепроверяет данные после диалогов подтверждения. Python-lock и Apps Script-lock не являются одним общим замком, ручной пользователь Sheets не участвует в транзакции Python. Это меры обнаружения конфликтов и ограничения записи, а не обещание атомарной транзакции над всей книгой. При maintenance пользователь не должен вручную править источник. Неоднозначную финансовую запись нельзя автоматически повторять.

В legacy проверка пустой строки/запись и сверка снимка/удаление также выполняются отдельными API-запросами. Обе версии требуют осторожного восстановления после неясного результата, но только v2 имеет специализированный журнал применения категорий.

## Границы известных сведений о реальных книгах

- В старом экспорте PnL.xlsx были фиксированные формулы, 14 расходных категорий и validation до строки 155. Это историческое свидетельство о том экспорте, не утверждение о каждой ячейке нынешней рабочей книги `1I6_HFC…`.
- Для v2 владелец согласовал «Штрафы», сохранение только Whoosh в транспорте при отдельном «Самокат» в «Еда офис», сохранение активности обсуждавшейся спортивной подкатегории. Это решения миграции тестовой копии, не доказательство таких же названий в рабочей книге.
- Тестовая книга использовалась для синтетических сценариев и может содержать тестовые категории/архивные колонки. Их наличие не является финансовой истиной и не разрешает перенос в production или автономное удаление.
- GitHub Actions устанавливает Python/Docker-код, но не исходники Apps Script. В main лежит legacy `data/macros.gs`; в feature — v2 `data/macros.gs` и сохранённый `data/macros-v1.gs`. Сверять нужно исходник правильной ветки с bound-проектом конкретной книги.
- Два бота отвечают после последних передеплоев — подтверждено владельцем 2026-11-12. Это не заменяет полный аудит формул, прав, onEdit и всех сценариев категорий.
