# Purpose

Разделить legacy-контракт рабочей таблицы и v2-контракт тестовой. Одинаковые видимые листы и названия кнопок не означают одинаковую модель данных. Источники: `main` и `feature/manage-categories`, миграционные артефакты, согласованные владельцем правила и результаты тестов. Это описание программных контрактов; оно не является свежей побайтовой инвентаризацией двух живых книг.

Привязки и развёрнутые версии: [карта окружений](../../context/09-environments-and-branches.md). Рабочая книга не мигрировалась к v2 в рамках последних выпусков. V2-копия развивается независимо; одинаковые суммы, периоды, категории и операции между книгами не предполагаются.

## Сравнение контрактов

| Область | Рабочая legacy/v1, ветка main | Тестовая v2, ветка feature/manage-categories |
| --- | --- | --- |
| Доступ из Python | `GoogleSheetsStore` | `V2GoogleSheetsStore` поверх общего клиента |
| Основные видимые листы | «Траты», «Категории», «Аналитика», «Архив», месячные снимки | Те же назначения, плюс служебная модель v2 |
| Пользовательская операция | A:F: дата, категория, подкатегория, сумма, тип, примечание | A:F сохранены; G:K содержат пять служебных полей |
| Идентичность категории | Текстовое название и тип | Постоянный category_id, отображаемое имя, active, период деактивации |
| Идентичность подкатегории | Название в категории | Постоянный subcategory_id и current_category_id |
| Исторический родитель | Отдельного ID операции и реестра старых пар нет | В операции собственный category_id; прежние пары сохраняются отдельно |
| Идентичность операции | Физическая строка и снимок A:F при удалении | transaction_id, снимок связей, физическая строка и проверка её значений |
| «Категории» A:C | Источник вариантов ввода; Тип / Категория / Подкатегория | Генерируемый вид активных пар, а не источник истины |
| Доходы | Адаптер нормализует категорию в «Доход» | Сохраняются отдельные категории дохода; бот предлагает выбор, если их несколько |
| Новая строка из бота | Первая пустая дата в A, даже если B:F заполнены | Полностью свободная пользовательская строка; частичный ввод не перезаписывается как пустой |
| Даты | Бот записывает текст ДД.ММ.ГГГГ с RAW | Видимая дата сохраняется, числовая report_date в K используется для расчёта |
| Готовность данных | Обязательных meta/schema gates нет | Scope, schema=2, revision, ready/open и отсутствие pending |
| Ручной ввод | Зависит от существующих формул и валидаций книги | onEdit/полная сверка обновляют ID, снимки и validation_state |
| Побочные записи при чтении | Чтение последних операций/аналитики само не ведёт v2-снимки | Эти действия проходят `_ledger` и могут записывать G:K и служебные снимки |
| Месячная аналитика | Чтение рассчитанных подписанных блоков | Перед отчётом сверка строк и F1=ready; расчёт по сохранённым ID/датам |
| Детализация в боте | Четыре фиксированные категории | Динамические страницы по восемь, callback по category_id |
| Управление категориями | Кнопки нет | `/categories`, создание, переименование, перенос, деактивация и восстановление с подтверждением |
| Макрос из Git | Фиксированные B9:B22, 14 расходных категорий | Реестры, независимая сверка итогов, стабильный индекс архивных колонок |
| Снимок месяца | Значения «Аналитики», не исходные операции | Читаемый dashboard со значениями и диаграммами, ID в отдельном индексе |
| Защита очистки в макросе | Legacy-исходник не содержит отдельного подтверждения очистки | Отдельное подтверждение, проверки периода и неизменности данных |
| Восстановление изменения категорий | Сервиса нет | Maintenance/pending, точный приватный план с request_id, продолжение и подтверждённый откат |
| Предел изоляции | Свой spreadsheet_id | Свой spreadsheet_id и журналы, не общий реестр с рабочей книгой |

Legacy здесь — имя программного контракта. В рабочей книге не предполагается наличие ячейки `schema_version=1`: обязательные метаданные появляются только в v2.

## Структура v2 по листам

### Пользовательская операция «Траты»

| Колонка | Заголовок | Значение / правило |
| --- | --- | --- |
| A | Дата | Видимая дата операции |
| B | Категория | Читаемая подпись категории |
| C | Подкатегория | Читаемая подпись подкатегории |
| D | Сумма | Положительная конечная сумма; ввод бота по-прежнему в целых рублях |
| E | Доход/Расход | Поддержанные типы «Доход» и «Расход» |
| F | Примечание | Пользовательский текст |
| G | category_id | Историческая категория именно этой операции |
| H | subcategory_id | Постоянная подкатегория |
| I | transaction_id | UUID операции; не копировать в новую строку |
| J | validation_state | valid либо диагностическое состояние; пусто у пустой строки |
| K | report_date | Числовая дата Sheets для формул |

G:K могут быть скрыты, но являются частью строки. Перестановка или сортировка только A:F нарушает идентичность; переносить строку целиком A:K. Нельзя «чинить» J вручную на valid без сверки. Числовая дата, Date Sheets и текст ДД.ММ.ГГГГ / YYYY-MM-DD нормализуются; недопустимая дата не превращается в нулевую сумму.

### Служебные листы

| Лист | Заголовки / ключи | Назначение |
| --- | --- | --- |
| `_financebot_meta` | key, value | spreadsheet_id, schema_version, taxonomy_revision, migration_state, access_mode, pending_request_id |
| `_financebot_categories` | category_id, type, name, active, deactivated_period | Категории, включая неактивные |
| `_financebot_subcategories` | subcategory_id, current_category_id, name, active | Текущий родитель и активность подкатегории |
| `_financebot_category_history` | category_id, subcategory_id | Допустимые исторические пары |
| `_financebot_row_snapshots` | transaction_id, category_id, subcategory_id, category_label, subcategory_label, transaction_type | Доверенные связи до ручной правки |
| `_financebot_detail` | category_id, subcategory_id, category, subcategory, amount | Детализация по историческим парам выбранного периода |
| `_financebot_archive_columns` | category_id, column | Неизменное соответствие категории и колонки сводного архива |
| `_financebot_archive_labels` | sheet, cell, kind, category_id, subcategory_id | Адреса индексированных подписей аналитики и старых снимков |

Служебные листы могут быть скрыты/защищены оформлением миграции. Скрытие не является разграничением доступа. Произвольное ручное изменение UUID, метаданных и индексов не поддерживается. Восстановление исходных удалённых операций из агрегированного архива не гарантируется ни одной версией.

## Сверка при чтении

Сверка `_ledger` используется также перед добавлением, просмотром последних операций и удалением. Поэтому незавершённая ручная строка может временно блокировать эти действия, а не только месячную аналитику. Обновление служебных G:K и `_financebot_row_snapshots` возможно даже при команде просмотра; пользовательские A:F этим этапом не переписываются. Тестовый release_check использует каталог, статус и варианты ввода, а не эти методы с побочной записью.

## Requirements

### Requirement: Контракт выбирается по окружению
Клиент MUST работать с явно выбранной книгой и совместимым адаптером. V2 MUST не переходить автоматически на текстовый legacy-реестр при отсутствии служебных листов. Совпадение видимых A:F MUST не трактоваться как завершённая миграция.

#### Scenario: Скопированная v2-книга
- **WHEN** книга скопирована и получила новый spreadsheet_id
- **THEN** прежние метаданные scope не принимаются как корректные для нового ID; требуется явная подготовка и проверка новой области.

### Requirement: Источник истины справочника
В legacy варианты SHALL читаться из A:C «Категории». В v2 источником истины MUST быть служебные реестры и revision; вид «Категории» SHALL генерироваться из активных пар. Правка представления вне сервиса SHALL приводить к ошибке согласованности, а не к молчаливому изменению реестра.

#### Scenario: Название изменили вручную в «Категории»
- **WHEN** представление v2 расходится с реестром
- **THEN** бот требует восстановления согласованности; изменение не считается глобальным переименованием.

### Requirement: Имена и постоянные ID
V2 SHALL сохранять UUID при переименовании. Имена категорий SHALL быть уникальны после нормализации внутри типа, подкатегорий — внутри текущего родителя, включая неактивные сущности. Одинаковые названия в разных допустимых контекстах SHALL не объединять их ID.

#### Scenario: Переименование исторической сущности
- **WHEN** подтверждено новое имя активной или неактивной сущности
- **THEN** меняются связанные подписи операций, отчётов и индексированных архивов, но не суммы, UUID и историческая принадлежность операции.

### Requirement: Перенос для новых операций
V2 MUST сохранять прежний category_id существующих операций при переносе подкатегории. Перенос SHALL быть разрешён только между активными категориями одного типа без конфликта имени.

#### Scenario: Старая и новая траты
- **WHEN** использованная подкатегория перенесена из A в B
- **THEN** старая трата остаётся в A, новая выбирает B; неизменный subcategory_id связывает их с одной подкатегорией.

### Requirement: Удаление означает деактивацию
V2 MUST исключать неактивную сущность из новых вариантов без удаления исторических операций и архивных колонок. Неактивная категория MUST хранить период деактивации YYYY-MM. После подтверждённого восстановления ограничение для новых операций SHALL сниматься без изменения уже сохранённых архивных сумм.

#### Scenario: Архив после деактивации
- **WHEN** закрывается период деактивации категории
- **THEN** её колонка содержит фактическую сумму этого периода; за более поздние периоды до восстановления — нули, прежние архивные суммы сохраняются.

### Requirement: Сверка ручных строк
V2 MUST сверять пользовательские A:F с текущими реестрами и доверенными снимками, обновлять служебные поля и обнаруживать дубли/подмену ID. Несовместимые или незавершённые строки SHALL блокировать полный отчёт и архивацию вместо выдачи неполных итогов.

#### Scenario: Частично введённая строка
- **WHEN** дата пуста, но другие пользовательские ячейки заполнены
- **THEN** v2 не использует строку для новой траты и не перезаписывает её A:F как свободные.

#### Scenario: Историческая пара
- **WHEN** старая операция с неактивной или перенесённой подкатегорией имеет доверенный снимок
- **THEN** её историческая пара сохраняется; произвольно вставленные UUID сами по себе такого права не дают.

### Requirement: API и onEdit
V2-бот MUST сам записывать служебные поля для своих операций; изменения через API SHALL не полагаться на автоматический запуск onEdit. Обновление справочника SHALL обновлять зависимые списки ручного ввода до публикации ready. Связанный Apps Script SHALL обеспечивать onEdit и полную сверку ручного ввода в самой книге.

#### Scenario: Добавили подкатегорию через бота
- **WHEN** подтверждённое изменение завершено
- **THEN** новый вариант появляется в боте и соответствующих validation rules Sheets без ручного редактирования макроса и без ожидания onEdit от API.

#### Scenario: Сбой ручного триггера
- **WHEN** ручная строка не получила служебные поля
- **THEN** владелец проверяет bound Apps Script и при необходимости запускает refreshFinanceBotRows; не переносит служебные ID из соседней траты.

### Requirement: Аналитика по идентичности
V2 SHALL считать выбранный период по report_date и сохранённой паре category_id/subcategory_id. Перед выдачей отчёта SHALL выполняться сверка строк и проверка ready. Суммы категорий/подкатегорий SHALL не смешиваться только из-за совпадения названий.

#### Scenario: Две одноимённые подкатегории
- **WHEN** разные категории содержат одинаковое название подкатегории
- **THEN** их ID и аналитика остаются раздельными.

#### Scenario: Месяц в таблице
- **WHEN** запрошена аналитика любого окружения
- **THEN** читается выбранный в D1/D2 период; календарный месяц запроса сам по себе его не переключает.

### Requirement: Динамический dashboard и архив
V2 SHALL поддерживать динамическую общую сводку категорий A9:D и служебную детализацию по ID, сохраняя существующий dashboard. Новая расходная категория SHALL расширять только общую сводку и источник существующей большой диаграммы. Изменение справочника MUST не добавлять новые видимые блоки и не создавать или удалять диаграммы. Архивные колонки SHALL оставаться связанными с ID без ручных переменных архиватора.

#### Scenario: Новый месячный снимок
- **WHEN** создаётся архив аналитики
- **THEN** замораживаются значения и читаемое оформление; служебные category_id/subcategory_id не накладываются на видимые блоки и не сдвигают их. Индексы подписей хранятся отдельно.

#### Scenario: Новая категория с несколькими подкатегориями
- **WHEN** пользователь подтверждает новую расходную категорию с двумя или более подкатегориями
- **THEN** появляется одна строка в общей сводке, существующая большая диаграмма учитывает её; количество диаграмм прежнее, отдельный блок новой категории и её диаграмма не создаются.

#### Scenario: Добавление подкатегории
- **WHEN** в существующую категорию добавлена подкатегория, в том числе вторая после единственной
- **THEN** она доступна для новых операций и служебной детализации, её расходы относятся к родителю; новая строка общей сводки, новый видимый блок и новая диаграмма не создаются.

#### Scenario: Категория дохода
- **WHEN** добавлена категория дохода
- **THEN** она доступна в соответствующем выборе операций; новая диаграмма не создаётся и в общую сводку расходных категорий она не включается.

### Requirement: Подтверждения архивации
V2-архиватор MUST проверить строки, период, согласованность итогов и неизменность данных после пользовательских диалогов. Замена существующего архива и очистка «Трат» SHALL требовать подтверждения. Данные других периодов SHALL не очищаться как траты закрываемого месяца.

#### Scenario: Отказ от очистки
- **WHEN** пользователь отклоняет очистку
- **THEN** исходные операции остаются; сохранённый архив не означает согласия на удаление.

#### Scenario: Частичный сбой архива
- **WHEN** архивирование уже изменило архив и завершилось ошибкой
- **THEN** обслуживание сохраняется для проверки; нельзя вручную объявлять open без восстановления согласованности.

### Requirement: Приватный подтверждённый план
Изменение справочника в v2 MUST иметь owner/scope, revision, source fingerprint и request_id. Предпросмотр SHALL не писать в Sheets. Устаревший источник или период SHALL требовать нового подтверждения. Частичное применение SHALL продолжаться либо откатываться по сохранённому плану, без создания новой сущности и без подмены исходного состояния.

#### Scenario: Подтверждение после новой траты
- **WHEN** после предпросмотра изменились исходные данные
- **THEN** старый план отклоняется без автоматического перепланирования и применения.

#### Scenario: Журнал потерян
- **WHEN** у pending-запроса отсутствует или повреждён точный журнал
- **THEN** изменение и автоматический откат блокируются до восстановления оператором; новый UUID не подменяет незавершённую операцию.

### Requirement: Заголовки сводного архива по идентичности
При переименовании категории v2 SHALL обновлять её заголовок в существующем листе «Архив» по сохранённому соответствию ID и колонки, включая колонки без записи в индексе подписей. Числа, порядок и количество колонок SHALL сохраняться. Неоднозначное или повреждённое соответствие MUST приводить к отказу до записи, без угадывания по текстовому имени.

#### Scenario: Категория добавлена после миграции
- **WHEN** переименована категория, для которой колонка создана последующей архивацией и не включена в индекс подписей
- **THEN** заголовок этой колонки меняется сразу после подтверждения, прежние и нулевые суммы остаются прежними; новая архивация для обновления имени не нужна.

#### Scenario: Неактивная категория и существующие снимки
- **WHEN** переименована неактивная категория
- **THEN** её сводный заголовок и существующие индексированные исторические подписи обновляются; отсутствующие месячные снимки по-прежнему пропускаются с предупреждением и без создания листов.

#### Scenario: Неоднозначная колонка
- **WHEN** двум ID назначена одна колонка, одному ID несколько колонок или колонка пересекается с фиксированными итогами
- **THEN** переименование отклоняется до записи с объяснением конфликта.

### Requirement: Диагностируемое продолжение изменения
При сбое v2 SHALL сохранять этап, безопасную причину и число попыток запроса и показывать доступные «Продолжить» и «Откатить изменение». Продолжение MUST проверять фактический результат неопределённой записи перед её повтором, не создавать дубликатов и не повторять детерминированные конфликты как временные ошибки. Финансовые значения MUST не попадать в обычные диагностические сообщения.

#### Scenario: Ответ потерян после успешной записи
- **WHEN** Google принял запись, но подтверждение не получено
- **THEN** продолжение распознаёт уже выполненный шаг чтением и продолжает тот же запрос без повторного эффекта.

#### Scenario: Временная ошибка
- **WHEN** возникает временная ошибка доступа к Google
- **THEN** ограниченные повторы завершаются либо успехом, либо понятным сохранённым статусом; бесконечного цикла и автоматического отката после трёх неудач нет.

#### Scenario: Конфликт данных или периода
- **WHEN** финальная проверка обнаруживает изменённую пользователем ячейку или период
- **THEN** бот сообщает этап и расположение конфликта без финансового содержимого; бесконечные повторные подтверждения не предлагаются как решение, доступны безопасный откат либо восстановление оператором.

### Requirement: Подтверждённый откат незавершённого запроса
Владелец SHALL иметь кнопку «Откатить изменение» для незавершённой поддерживаемой операции и отдельное подтверждение. Откат MUST возвращать только изменения этого запроса, сохраняя последующие ручные правки, операции, суммы, даты и другие архивы. При конфликте откатываемого поля операция SHALL остановиться с объяснением. Успех SHALL публиковаться только после проверки восстановленной согласованности.

#### Scenario: Откат частичного переименования
- **WHEN** владелец подтверждает откат после изменения части подписей
- **THEN** выполненные изменения имён, реестров, проекций и зависимых списков возвращаются к исходным; запрос получает конечный статус отката, книга открывается только после успешной проверки.

#### Scenario: Отмена подтверждения отката
- **WHEN** владелец отказывается от подтверждения отката или закрывает окно
- **THEN** откат не выполняется; закрытие окна не объявляется отменой уже записанного изменения.

#### Scenario: Сторонняя правка
- **WHEN** изменена ячейка вне записей запроса, например D1 при переименовании
- **THEN** откат сохраняет её текущее значение; если менялась откатываемая подпись или появилась операция с зависимостью от создаваемого ID, бот блокирует несовместимый откат до записи и объясняет конфликт.

#### Scenario: Повтор и перезапуск отката
- **WHEN** процесс перезапущен или подтверждение отката повторено после частичного выполнения
- **THEN** продолжается тот же откат по журналу; применение и откат не выполняются одновременно, revision не возвращается к старому номеру, завершённый откат не повторяет записи.

#### Scenario: Старый неподдерживаемый журнал
- **WHEN** исходное состояние старого запроса недостаточно для проверяемого отката
- **THEN** бот объясняет необходимость восстановления оператором; не угадывает исходные значения и не снимает maintenance вручную.

### Requirement: Восстановление неактивных сущностей
V2 SHALL предоставлять подтверждаемую кнопку «Восстановить» для неактивной категории и подкатегории. Категория SHALL возвращаться вместе со всеми её текущими подкатегориями, с прежними ID и историческими связями. Подкатегория отдельно SHALL восстанавливаться только при активном родителе. Восстановление MUST не переписывать сохранённые архивные значения и не добавлять видимые блоки или диаграммы.

#### Scenario: Восстановление категории целиком
- **WHEN** владелец подтверждает восстановление категории
- **THEN** категория и все текущие подкатегории становятся активными, включая отдельно отключённые; перенесённые к другому родителю не затрагиваются, список затрагиваемых сущностей показан до подтверждения.

#### Scenario: Восстановление подкатегории
- **WHEN** владелец подтверждает восстановление неактивной подкатегории у активного родителя
- **THEN** возвращается только она с прежним ID; другие неактивные сущности не активируются.

#### Scenario: Родитель неактивен
- **WHEN** выбрано отдельное восстановление подкатегории неактивного родителя
- **THEN** бот объясняет необходимость восстановления категории и не активирует родителя скрытым действием.

#### Scenario: Списки и новые операции
- **WHEN** восстановление завершено
- **THEN** варианты доступны в боте и выпадающих списках Sheets; новая операция и её архивация допустимы после восстановления, существующая архивная колонка используется без дублирования, прежние архивные числа не меняются.

#### Scenario: Повторное отключение
- **WHEN** восстановленная категория снова деактивирована
- **THEN** применяется новый период деактивации и сохраняется история; повтор восстановления или сетевого запроса не создаёт новых ID и колонок.

### Requirement: Исторический индекс не блокирует несвязанные изменения
Создание категории/подкатегории, перенос и деактивация MUST не требовать существования старого снимка, подписи которого не меняются этими действиями. Такие изменения SHALL сохранять исторические записи индекса без автоматического удаления и не создавать отсутствующие архивы.

#### Scenario: Новая категория после удаления старого снимка вручную
- **WHEN** у ИФТ-книги есть запись индекса для отсутствующего архивного листа и пользователь вводит новую категорию с допустимыми подкатегориями
- **THEN** бот показывает предпросмотр; до подтверждения нет записи в Sheets, после подтверждения категория применяется без создания или очистки старых архивов.

#### Scenario: Переименование при отсутствующем снимке
- **WHEN** глобальное переименование требует индексированного архива, которого нет
- **THEN** отсутствующий месячный снимок «Архив (…)» пропускается с предупреждением по требованию «Переименование при отсутствующих архивных снимках»; остальные существующие представления обновляются, отсутствующий лист не создаётся и его индекс сохраняется. Иные ошибки индекса блокируют изменение.

### Requirement: Наблюдаемый исход создания категории
Ввод подкатегорий SHALL приводить к предпросмотру либо видимой ошибке с возможностью повторного ввода. Диалог MUST не закрываться без явной отмены или перехода в другой сценарий. Закрытие SHALL сохранять в истории сообщения об ошибке, предпросмотре и успешном применении.

#### Scenario: Список подкатегорий
- **WHEN** введены «Белье», «Верхняя одежда», «Одежда», «Аксессуары» отдельными строками
- **THEN** в предпросмотре показаны категория и все четыре подкатегории; действие не выполняется до подтверждения.

#### Scenario: Ошибка подготовки
- **WHEN** подготовка плана возвращает ошибку
- **THEN** бот объясняет ошибку и сохраняет черновик для исправления; последующая отмена не заменяет текст ошибки общим «закрыто».

#### Scenario: Подтверждение и закрытие
- **WHEN** пользователь подтверждает применённое создание и затем закрывает меню
- **THEN** факт успеха остаётся в переписке, повтор старого подтверждения не создаёт дубль.

### Requirement: Исправление выпускается только на ИФТ
Исправление MUST разворачиваться из feature/manage-categories существующим Test stand workflow по test-тегу. Main, v-теги, production Compose/env, рабочий контейнер и рабочая таблица SHALL оставаться без изменения.

#### Scenario: Успешные проверки
- **WHEN** регрессионные, полные Python/Node и OpenSpec-проверки пройдены
- **THEN** допускается автоматический test deploy; рабочий deploy не запускается, финансовые данные в обеих книгах не создаются для проверки без подтверждения владельца.

### Requirement: Сохранение диаграмм при изменении справочника
Обычное изменение справочника MUST сохранять количество, идентификаторы, положение, размеры и оформление существующих диаграмм. При создании категории/подкатегории заголовки и настройки прочих диаграмм SHALL не меняться. Изменять источник данных разрешается только у общей диаграммы категорий для расширения сводки.

#### Scenario: Пользовательское оформление
- **WHEN** владелец изменил цвета, подписи или размещение диаграмм и затем добавил категорию
- **THEN** его оформление и chart ID сохраняются; диаграммы не заменяются заново созданными объектами.

#### Scenario: Повторное применение
- **WHEN** подтверждение повторено или запрос восстановлен после частичного сбоя
- **THEN** ни дополнительная диаграмма, ни повторная строка общей сводки не создаются.

### Requirement: Сохранение незатрагиваемых областей аналитики
При создании категории/подкатегории v2 SHALL сохранять прочие видимые блоки, их формулы, форматирование и порядок. Месяц и год MUST не переключаться. Существующие значения продолжают пересчитываться; создание справочника само по себе не разрешает перестраивать видимую детализацию подкатегорий.

#### Scenario: Новый вариант внутри категории
- **WHEN** к категории добавляется подкатегория
- **THEN** существующие малые диаграммы и их диапазоны остаются прежними; новая подкатегория не становится отдельной категорией общей сводки.

#### Scenario: Недостаточно места
- **WHEN** новая строка общей сводки затронет существующий блок или диаграмму
- **THEN** изменение отклоняется до записи с объяснением конфликта размещения; dashboard не сдвигается автоматически.

### Requirement: Однозначная общая диаграмма
Бот SHALL изменять только существующую диаграмму, однозначно связанную с общей сводкой. Если источник диаграммы нельзя определить безопасно, создание нового объекта или выбор произвольной диаграммы MUST быть запрещены.

#### Scenario: Общая диаграмма отсутствует или неоднозначна
- **WHEN** перед изменением не удаётся однозначно определить существующую общую диаграмму и её источник
- **THEN** пользователь получает объяснение до записи; никакая диаграмма не создаётся, не удаляется и не перенастраивается по догадке.

### Requirement: Следующий месяц после закрытия отчёта
V2-архиватор SHALL после проверенного сохранения архива и подтверждённой успешной очистки операций переключать «Аналитика»!D1 на следующий месяц относительно закрытого периода. Для декабря SHALL записывать D1=1 и увеличивать D2 на один; для остальных месяцев D2 SHALL оставаться без записи. Финальное уведомление SHALL сообщать о переключении вместо просьбы сделать его вручную.

#### Scenario: Обычный месяц
- **WHEN** успешно завершено закрытие октября 2026 года с подтверждённой очисткой операций
- **THEN** в текущей аналитике D1=11, D2=2026; D2 не перезаписывается, архив остаётся отчётом за октябрь 2026 года.

#### Scenario: Переход года
- **WHEN** успешно завершено закрытие декабря 2026 года с подтверждённой очисткой операций
- **THEN** в текущей аналитике D1=1 и D2=2027; архивные имя, период и суммы остаются декабрьскими за 2026 год.

#### Scenario: Переход от выбранного периода
- **WHEN** успешно закрыт выбранный в D1/D2 период, отличающийся от текущей календарной даты
- **THEN** следующий период вычисляется от закрытого месяца и года, а не от даты запуска.

#### Scenario: Отмена или ошибка до переключения
- **WHEN** пользователь отклоняет замену архива или очистку операций либо выполнение завершается ошибкой до шага переключения
- **THEN** D1 и D2 сохраняют исходные значения; существующие правила сохранения архива, подтверждений и обработки ошибок остаются прежними.

#### Scenario: Сохранение остального поведения
- **WHEN** выполняется закрытие месяца с автоматическим переходом
- **THEN** единственные новые записи в текущую аналитику — D1 и при переходе года D2; формулы, диаграммы, категории, архивные колонки и порядок существующих подтверждений не меняются.

### Requirement: Переименование при отсутствующих архивных снимках
V2 SHALL разрешать подтверждённое переименование активных и неактивных категорий и подкатегорий, если индекс содержит ссылки на отсутствующие месячные снимки. Подписи SHALL обновляться во всех существующих индексированных листах и операциях с сохранением ID, сумм, дат и связей. Отсутствующие снимки MUST не создаваться заново; их ссылки MUST не удаляться из индекса.

#### Scenario: Переименование категории
- **WHEN** пользователь переименовывает активную или неактивную категорию при отсутствующем месячном снимке
- **THEN** предпросмотр доступен и после подтверждения новое имя появляется в существующих операциях, аналитике, служебных проекциях и индексированных архивах; финансовые значения и ID прежние.

#### Scenario: Переименование подкатегории
- **WHEN** пользователь переименовывает активную или неактивную подкатегорию, включая ранее перенесённую, при отсутствующем месячном снимке
- **THEN** подтверждённое имя обновляется в существующей истории по её ID без изменения исторического родителя и сумм.

#### Scenario: Несвязанный отсутствующий архив
- **WHEN** отсутствующий снимок индексирован для другой категории
- **THEN** он не блокирует выбранное переименование; его лист не восстанавливается и ссылка сохраняется.

### Requirement: Явное предупреждение о пропущенных снимках
При предпросмотре переименования v2 SHALL сообщать число уникальных отсутствующих месячных снимков, пропущенных при обновлении, и что они не восстановлены. Предпросмотр MUST не изменять Sheets; сохранённое подтверждение, revision и проверка источника SHALL оставаться обязательными.

#### Scenario: Предпросмотр с отсутствующими снимками
- **WHEN** готовится переименование с несколькими ссылками на один отсутствующий месячный снимок
- **THEN** предупреждение учитывает один лист, пользователь подтверждает этот результат; до подтверждения удалённых записей нет.

#### Scenario: Архив появился после предпросмотра
- **WHEN** до подтверждения восстановлен ранее отсутствующий лист или изменён индекс
- **THEN** прежний план отклоняется и требуется новый предпросмотр; доступный архив не пропускается по устаревшему плану.

### Requirement: Ограниченный пропуск отсутствующих листов
V2 MUST пропускать только ссылки на отсутствующие месячные снимки «Архив (…)». Отсутствие обязательного листа, неизвестная ссылка на иной отсутствующий лист или повреждение подписи в существующем листе SHALL блокировать переименование до записи. Исключения MUST не скрывать ошибки доступа Google.

#### Scenario: Отсутствует обязательный лист
- **WHEN** отсутствует «Аналитика», «Архив» или обязательный служебный лист
- **THEN** запрос отклоняется без записи вместо частичного переименования.

#### Scenario: Повреждённая существующая подпись
- **WHEN** индекс ссылается на неизвестный ID, неверный вид подписи или формулу вместо подписи в существующем листе
- **THEN** переименование отклоняется до записи; пропуск отсутствующих снимков не отключает действующие проверки.

## Отличия интерфейса бота

Legacy имеет десять кнопок в пяти рядах и сворачиваемое reply-меню. V2 сохраняет эти кнопки и добавляет шестой ряд «Категории», `/categories`, фильтр активности, страницы по восемь и выбор сущности по UUID. Новая категория создаётся через тип → имя → 1–20 подкатегорий строками → подтверждение; имя ограничено 1–64 символами с нормализацией пробелов. Доступны добавление подкатегории, rename, move, deactivate и подтверждаемое восстановление. Категория восстанавливается со всеми текущими подкатегориями; отдельная подкатегория требует активного родителя. Для незавершённого поддерживаемого запроса доступны диагностика, продолжение и подтверждённый откат. Смена типа существующей категории не реализована.

В обоих окружениях запись и удаление финансовой операции требуют подтверждения. «Выбрать для удаления» показывает последние десять операций, а не полный редактор всей истории. Удаление операции физически удаляет строку; оно не равно кнопке удаления категории, которая в v2 означает деактивацию. Полного Telegram-редактора произвольной старой траты пока нет. Последние операции показываются по порядку строк листа, не путём сортировки по календарной дате.

## Согласованность и ограничения конкурентного доступа

V2-адаптер использует RLock своего store, повторное чтение источника, revision и fingerprint. Apps Script использует document lock и перепроверяет данные после диалогов подтверждения. Python-lock и Apps Script-lock не являются одним общим замком, ручной пользователь Sheets не участвует в транзакции Python. Это меры обнаружения конфликтов и ограничения записи, а не обещание атомарной транзакции над всей книгой. При maintenance пользователь не должен вручную править источник. Неоднозначную финансовую запись нельзя автоматически повторять.

В legacy проверка пустой строки/запись и сверка снимка/удаление также выполняются отдельными API-запросами. Обе версии требуют осторожного восстановления после неясного результата, но только v2 имеет специализированный журнал применения категорий.

## Границы известных сведений о реальных книгах
