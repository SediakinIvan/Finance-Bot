# Design

## Context

См. proposal.md и specs/. Основа принята, 22 задачи выполнены. `category_changes.prepare_change` и native apply уже поддерживают create/rename/move/deactivate, source fingerprint, revision и request_id. `V2GoogleSheetsStore.apply_category_change` использует общий lock адаптера. В bot.py один ConversationHandler, общий сброс диалога и отдельная проверка callback-доступа. Новых кнопок справочника нет.

В compose.yaml контейнер read_only и только /tmp доступен временно; существующий journal требует постоянного приватного каталога. Google UI и Apps Script не разделяют Python-lock. Архиватор уже проверен; его бизнес-правила не переписываются.

## Goals / Non-Goals

**Goals:** тонкий Telegram-интерфейс поверх принятого сервиса, согласованный предпросмотр/подтверждение, восстановление запроса после сбоя без повторной записи.

**Non-Goals:** новая БД, новый механизм архивации, автоматическое исправление ручных финансовых правок, реактивация, полноценный редактор операций, автоматическое разрешение частичных сбоев без проверки.

## Decisions

### Диалоги и навигация

Добавить отдельный модуль диалога, интегрируемый с существующей машиной состояний, а не разрастать bot.py доменными правилами. Callback-префикс `tax:` отделён от существующего `cat:` ввода операции. Кнопка «Категории» добавляется шестым рядом: остальные десять кнопок сохраняются. Все списки постраничные, по восемь сущностей. Тип категории выбирается при создании; существующий тип не редактируется.

Карточка категории: подкатегории, «Добавить подкатегорию», «Переименовать», «Удалить», «Назад». У активной подкатегории также есть «Перенести». У неактивных сущностей доступны просмотр и переименование; история не становится новым выбором для операций. Исторические пары после переноса не дублируются как текущие подкатегории старого родителя.

Создание: тип → имя → список подкатегорий отдельными строками → предпросмотр. Добавление: имя → предпросмотр. Переименование: новое имя → предпросмотр. Перенос: активный получатель того же типа → предпросмотр. Удаление: последствия и выбранный D1:D2 период → подтверждение. Названия предлагается ограничить 1–64 символами, список одного создания — 1–20 строками; пробелы нормализуются, дубли отклоняются. Позже можно добавлять подкатегории отдельно. Эти пределы относятся к одному диалогу, не к размеру справочника.

«Отмена», /cancel и переход в другой основной сценарий удаляют незаписанный план и токены. Диалог категории и диалог траты не должны одновременно владеть вводом текста. Если изменение уже применяется, отмена не является откатом; пользователь получает статус.

### Подготовка и подтверждение

Адаптер получает реестр, снимок и готовит план вне Telegram event loop через asyncio.to_thread. Предпросмотр показывает старое/новое название или родителя, смысл деактивации, её период, число затронутых операций/архивов без финансовых подробностей. В диалоге хранится непрозрачный токен, область пользователя/таблицы, revision, request_id и ссылка на точный приватный план. UUID сущности не заменяется индексом страницы; callback укладывается в 64 байта.

До подтверждения нет записи в Sheets. Подтверждение проверяет владельца, личный чат, активный токен и исходный план. Полный source fingerprint намеренно консервативен: даже новая трата после предпросмотра требует нового итога и подтверждения. Отдельно проверяется период деактивации. Автоматический replan с последующим применением без нового подтверждения запрещён.

### Применение, журнал и восстановление

Переиспользовать внутренний сервис и lock адаптера. Добавить минимальные методы preview/apply/status/resume: Telegram не должен напрямую получать gspread-клиент. В памяти на пользователя один активный план; повтор callback сверяется со статусом request_id и не создаёт новый запрос.

`CATEGORY_CHANGE_STATE_DIR` указывает на приватный каталог с подкаталогами таблицы и request_id. Файлы плана/журнала 0600, каталог 0700, вне Git. В compose добавить отдельный RW bind mount под UID 10001; root filesystem остаётся read_only, ключ Google — RO. При недоступном журнале управление показывает ошибку до изменения таблицы. Сбой после write не повторяет финансовую запись; метаданные и журнал определяют продолжение. Завершённый request возвращает сохранённый результат.

После рестарта неподтверждённый предпросмотр требует нового диалога. Для pending request бот показывает статус и кнопку подтверждаемого продолжения того же сохранённого плана. Если журнал отсутствует/не совпадает, никаких догадок: сообщение о необходимости восстановления оператором и блокировка записи сохраняются.

В preview пользователь получает предупреждение не редактировать таблицу во время применения. Перепроверки источника остаются обязательными; общей транзакции с владельцем Google Sheets нет. Зависимые списки ручного ввода должны обновляться при изменении справочника; одной доставки onEdit для API-изменения недостаточно. Обновление списков включается в применение до объявления успеха, с сохранением допустимых исторических пар строк.

## Risks / Trade-offs

- [Много запросов Sheets] → пакетное чтение реестров, переиспользование известных sheetId, статус выполнения, ограниченный backoff только GET/429. Автоповтор неоднозначного write не добавлять.
- [Случайный клик/старая кнопка] → подтверждение, токен, owner/scope/revision, request_id и одноразовое применение.
- [Падение контейнера] → постоянный журнал и подтверждаемое продолжение; /tmp не использовать как единственную копию.
- [Ручная правка во время изменения] → maintenance и проверка финансовых значений перед каждым шагом; остановка вместо перезаписи.
- [Длинные имена/списки] → ограничение входа одного диалога, страницы, разбиение предпросмотра; не усекать сами сохранённые названия молча.

## Migration Plan

Разработка и тесты используют schema_version=2 и отдельный тестовый токен/таблицу. Перед рабочим включением: перенести принятую основу в основные specs, подготовить каталог журнала и права, согласованно установить текущий Apps Script и мигрировать рабочие таблицы, затем релиз бота. Один polling-процесс на токен. Откат v1 не подключать к v2 автоматически: остановить записи и использовать согласованную резервную копию; после новых операций требуется отдельный план сохранения данных.
