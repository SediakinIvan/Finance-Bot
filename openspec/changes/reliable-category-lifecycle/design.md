# Design

## Context

См. proposal.md. Исследованы category_changes, category_changes_native, category_management, category_ui, taxonomy, category_schema, category_projections, migration_apply, dropdown helpers, соседние тесты и текущий архиватор.

Наблюдения:

- Rename обновляет «Архив» через `_financebot_archive_labels`. Первичная миграция заполняет его для старых колонок; `saveMonthlyReport` добавляет новые соответствия в `_financebot_archive_columns`, но не регистрирует их заголовки в индексе подписей. Это конкретный путь появления необновлённого заголовка.
- Native apply перечитывает книгу для каждого изменённого листа, записывает часть сервисных листов целиком, хранит completed по листам и в конце сравнивает снимок всей книги. Между успешной записью и сохранением completed возможен сбой. Исключение скрывается общим «Изменение не завершено» без этапа и причины.
- Последний реально проверенный зависший запрос уже применил все листы. С планом расходились D1 и удалённые дата/служебные поля строки. Восстановление после отдельного согласования сохранило ручные правки. Это подтверждённый случай внешнего конфликта, но не доказательство причины всех повторяющихся сбоев. Сетевые сбои и неопределённый исход должны воспроизводиться тестами, а не объявляться установленной причиной.
- В UI есть preview cancel, но у pending только «Продолжить» и «Закрыть». Реактивации нет; активной категории запрещён непустой deactivated_period. Category деактивирует текущих детей, включая сохранение исторических пар.

## Goals / Non-Goals

**Goals:** устранить конкретную рассогласованность архивных заголовков; сделать состояния применения/продолжения/отката наблюдаемыми и восстанавливаемыми; вернуть активность с прежней идентичностью.

**Non-Goals:** атомарная транзакция всей Google-книги, откат произвольной завершённой истории, автономное принятие конфликтующих финансовых правок, удаление архивных колонок, новые диаграммы, перерасчёт сохранённых архивов, обновление макроса или прома.

## Decisions

### 1. Заголовки из реестра колонок

Для rename расходной категории использовать `_financebot_archive_columns` как источник ID→номер существующей колонки сводного «Архива». Проверить ID, уникальность в обе стороны, номер >4, отсутствие формулы в заголовке и существование колонки. Объединить эти подписи с архивным индексом в один согласованный набор изменений; при противоречии ID/координат отказать до write. Недостающую запись заголовка добавить в индекс в подтверждённом плане без удаления прежних записей. По имени или номеру в списке категорий колонку не угадывать. Существующие фиксированные итоги и числа не переписывать. Для доходной категории не создавать расходную колонку.

### 2. Журналируемые шаги и readback

До первой записи сохранять версию плана, исходный снимок, точные before/after изменяемых значений/формул и параметров validation/presentation. Шаг содержит тип/область, фазу prepared→written→verified, попытки и безопасную последнюю ошибку. Применять точечные записи по возможности вместо clear/rebuild сервисных таблиц; для добавленных/убранных строк сервисной проекции сохранять точные границы и обратные значения. Денежные и пользовательские даты не включать в операции записи rename.

При resume сначала читать текущие значения шага: after означает уже применён, before — допустима запись; третье состояние означает конфликт. Проверять выполненные шаги, а не доверять одному completed. После неопределённого ответа Google сначала readback. До трёх попыток одного шага с ограниченной задержкой разрешать только для классифицированных временных ошибок, с readback между попытками; ошибки плана/доступа/конфликты не крутить как временные. Применение и rollback одного запроса сериализовать существующим store lock и durable phase gate; повторные callbacks не запускают вторую операцию.

Финальную проверку разделить на точность записанных полей, сохранение финансовых/исторических инвариантов и согласованность registry/view/dropdowns. Не сравнивать вычисляемые значения формул как константы. Изменение даты, суммы, операции, периода или связанной внешней сущности во время применения не принимать автоматически: показать конфликт с координатами; дать безопасный rollback либо операторское восстановление. Сбой после ready, но до локального complete, распознавать по точному результату и финальной revision.

В обычные логи и Telegram выводить request ID, этап, безопасный код, лист/координату, счётчик и доступное действие. Не выводить содержимое строк, имена финансовых контрагентов, токены и API response body. Детальные before/after остаются в приватном журнале с прежними 0700/0600.

### 3. Компенсирующий откат

Состояния запроса расширить фазами rollback_pending/rolling_back/rolled_back и conflict; учитывать их в status/pending, callbacks и release_check, не сбрасывать maintenance при деплое. «Закрыть» остаётся закрытием; «Откатить изменение» открывает отдельный preview с описанием возврата и подтверждением. Автоматический rollback после N ошибок отвергнут по предпочтению владельца.

До первой компенсации проверить все затрагиваемые поля и зависимости: допускаются before или after этого запроса, но не третье значение. Незаписанные поля не трогать. Если D1 не менялся запросом rename, оставить текущий D1, даже когда он отличается от source. Не возвращать полностью source-книгу и не переписывать A:F старым снимком. При конфликте самой подписи, удалённом существовавшем листе или новых операциях, ссылающихся на отменяемый ID, остановиться до компенсаций и показать операторский путь. Новые листы/архивы пользователя не удалять.

Откатывать проверенные записи в обратном порядке с write-ahead checkpoint и readback. Восстановить исходные имена/активность/исторические связи и зависимые списки. Native charts сохранять; если источник основной диаграммы был расширен этим запросом, вернуть только его прежний диапазон после проверки текущей spec. При сбое отката оставить книгу в maintenance и продолжать ту же rolling_back фазу; продолжение forward запрещено. После проверки исходной бизнес-модели с сохранением нетронутых ручных правок публиковать ready/open и revision строго больше ранее видимых номеров, затем terminal rolled_back. Повтор terminal callback не пишет повторно.

Старые планы без достаточных before/after и проверенного presentation не перепланировать: показать, почему требуется оператор. Полностью завершённые запросы сохраняют идемпотентный ответ. Текущий известный операторский recovery не является шаблоном автоматического согласия с любой правкой.

### 4. Реактивация

Добавить action reactivate в pure план, manager/store и UI неактивных сущностей. Для категории установить active=true, снять текущий deactivated_period и активировать **всех текущих детей**, включая ранее отдельно отключённых. Детей с другим current_category_id не трогать. В confirmation показать их список и количество. Для одной подкатегории требовать активного родителя; отдельную скрытую активацию родителя не выполнять.

Сохранить UUID, пары истории и расположение архивных колонок. Снятие текущего маркера деактивации разрешает последующие новые операции и проходит существующие Python/Apps Script проверки; не вводить новую схему или обязательную правку bound Apps Script. Уже сохранённые архивы и нули прошлых закрытых периодов не переписывать при реактивации. Повторная деактивация устанавливает новый текущий период. Пересборка старых архивов и исправление их исторических сумм не входят в восстановление.

Проверить нормализованные конфликты имён, актуальность плана и списки ручного ввода. При восстановлении не добавлять строку уже существующей расходной категории или видимые блоки/диаграммы. Dropdowns согласовать с активным родителем по тем же правилам нормализации, что и разрешение пары операции.

## Risks / Trade-offs

- [Google не предоставляет транзакцию между запросами] → write-ahead шаги, readback и идемпотентная компенсация; не обещать безусловный откат при внешнем конфликте.
- [Откат стирает ручные правки] → перед компенсациями сравнить touched fields и зависимости, сохранять нетронутые поля; конфликт требует оператора.
- [Все дети восстанавливаются неожиданно] → это явный выбор владельца; список всех текущих детей показать до подтверждения.
- [Старый журнал не поддерживается] → диагностируемое ограничение до записи, без подмены плана и ручного сброса meta.
- [Сравнение всей книги даёт ложные отказы] → отделить formulas/вычисленные значения и координаты операций от нетронутых данных, не ослабляя финансовых инвариантов.

## Migration Plan

Данные транзакций и макрос не мигрируются. Новый формат только у приватных журналов будущих операций; совместимость pending и release_check проверяется отдельно. На apply воспроизвести все случаи fake-Google тестами с отказом до/после записи на каждом шаге, restart и конфликтами. Сделать снимок ИФТ перед живой приёмкой; произвольных синтетических архивов/категорий без нужды не создавать. Выпуск только тестовым пайплайном; main и рабочая книга прежние. Перед откатом версии бота убедиться, что нет нового rolling_back/pending журнала: старый образ не должен продолжать неизвестный формат.

## Уточнения после ручной приёмки

- Подтверждён выход target range 441 за grid rowCount 437. Перед изменениями должен существовать журналируемый capacity-шаг: расширить управляемый лист только до необходимого размера, выполнить readback, затем писать значения. Resume не расширяет повторно; компенсация возвращает значения, но не удаляет добавленные строки, чтобы не потерять пользовательские данные.
- Сверка ledger должна возвращать post-write состояние собственных служебных полей для последующего optimistic check append. Исходный пользовательский A:F и реальные конкурентные правки продолжают проверяться. Неизменённые snapshots/service не записываются повторно; свежая проверка scope/revision не требует перечитывать весь registry.
- HTTP-код/тип и безопасная история ошибок сохраняются после rollback. Отказ до отправки финансового batch отличается от неопределённого результата после отправки. Неопределённые финансовые записи автоматически не повторяются. Повторный полный readbook перед уже выполняемой native preflight-проверкой убирается без отмены source gate.
