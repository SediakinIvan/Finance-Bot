# Design

## Context

См. proposal.md, Why. Боевой ID — `1I6_HFCMVmxOD5buP6RdhtfJHld66tj7oMGArpW4AEC4`; эталон структуры ИФТ — `1jaEzmJPqYzxSp-HtDw-zwt_kPqSEs4enBrkG-Lc-UzA`. Эти ID остаются раздельными. Фактическое текущее содержимое живых книг в propose не проверялось.

Найдены существующие plan-native/install-copy/finalize-copy и миграционные тесты. Установщик защищает A:F, но пересоздаёт содержимое «Аналитика»/«Категории» и устанавливает dashboard через bootstrap. Это не доказательство безопасного переноса нынешней ИФТ-структуры. Для уже мигрированной книги prepare_migration отклоняет новый seeding: нужны сохранённые ID и отдельный согласованный upgrade.

В feature compose.yaml переопределяет GOOGLE_SHEET_ID тестовым ID. CI/CD уже содержит release_check перед заменой контейнера, однако использует конфигурацию выбранного коммита. Выпуск из main/v-тега требует исправленной production-привязки, а не копирования feature Compose без проверки. Текущие workflow собирают образ заново; одинаковый digest с ИФТ не гарантируется. Apps Script этими workflow не устанавливается.

## Goals / Non-Goals

**Goals:** воспроизводимый перенос структурного контракта с измеряемой сохранностью каждой исходной финансовой записи и архива; восстановление после частичной записи; согласованные книга, скрипт и бот.

**Non-Goals:** синхронизация данных между книгами, перенос тестового справочника/UUID, включение дополнительных аккаунтов, изменение продукта и месячное закрытие в ходе установки.

## Decisions

1. **Миграция существующей книги по её источнику.** Сохраняем рабочий ID и финансовую историю; справочник ПРОМ становится v2-реестром, его данные синхронизирует владелец. Не заменяем книгу клоном ИФТ: это переносит чужие scope/UUID и теряет расхождения данных. Эталон ИФТ используется для схемы, формул, поведения и оформления, адаптируемых под реальный состав ПРОМ.
2. **Приватный manifest до/после.** Нативная копия сохраняет возможности Sheets, отсутствующие в XLSX и миграционном snapshot: диаграммы, типы таблиц, защиты, validations. Отдельно фиксируем формулы, metadata листов, значения A:F, архивные суммы и подписи, D1/D2, исходник и триггеры Apps Script, конфигурацию и текущий образ. Секреты и финансовые строки не попадают в Git. Проверяем точное совпадение исходных финансовых полей и архивных ячеек; одного равенства общей суммы недостаточно.
3. **Проверка существующего установщика на репетиционной копии.** Сначала read-only diff двух живых структур и план на снимке ПРОМ. Разрешены только заранее перечисленные структурные изменения. Неизвестные области сохраняются. В частности, исключаем потерю ручных областей при worksheet.clear и появление лишних диаграмм bootstrap. Точечные изменения миграционного инструмента входят в реализацию, если нужны для этой гарантии. Все новые формулы пересчитываются на данных ПРОМ и сравниваются с независимым расчётом.
4. **Окно обслуживания вместо обещания атомарности.** После завершения синхронизации владельцем останавливаем production polling и ручные правки; снимаем окончательный backup и fingerprint. ИФТ остаётся работающим и неизменным. Нет общего lock Sheets/Python/UI; любое несовпадение источника останавливает применение. Шаги и before/after сохраняются в production-журнале, ready/open публикуется последним.
5. **Apps Script — отдельная поставка.** Сверяем фактически установленный ИФТ-исходник с Git, включая локальную правку смены месяца; она не считается установленной автоматически. Для ПРОМ используем точный зафиксированный совместимый исходник. При отсутствии разрешённого доступа к bound-проекту передаём владельцу файл для установки и ждём JSON verifyFinanceBotMigration для production ID и проверки onEdit. Простого копирования macros.gs в Git недостаточно.
6. **Существующий production-пайплайн.** Продвигаем принятый код ИФТ в main обычным merge с проверкой конфликтов и накопленных локальных правок. Исправляем только production-конфигурацию, сохраняем token и отдельный журнал, дополнительные аккаунты не включаем. Существующий release_check остаётся обязательным. Используем v-тег принятого main-коммита; не запускаем тестовый workflow против ПРОМ и не создаём второй polling с тем же токеном.
7. **Откат по состоянию данных.** До открытия записей допускается проверенное восстановление исходной структуры и Apps Script из backup в исходную книгу и запуск старого совместимого образа. Метод восстановления нативных объектов репетируется до первой production-записи; существующий restore-copy сам по себе не доказывает полноценный нативный rollback. После открытия сохраняем новые операции/ручные правки и выбираем совместимый forward-fix либо согласованный replay; старый backup не накатывается поверх новых данных. Смена рабочего ID не входит в автоматический откат.

## Risks / Trade-offs

- [Нативные метаданные не представлены в обычном snapshot] → полная нативная копия, отдельный manifest и репетиция восстановления; XLSX не является единственным backup.
- [Неоднозначные исторические имена] → точная карта соответствий с владельцем; остановка вместо потери/слияния категорий.
- [Частичный Google batch или 429] → контроль результата, ограниченные повторы, журнал и обслуживание; финансовые записи не повторяются вслепую.
- [Старый ПРОМ пишет во время изменения] → polling остановлен до изменения схемы, ручное окно подтверждено, fingerprint перепроверен.
- [Макрос отличается от Git] → сравнение установленного исходника, отдельное доказательство установки; не обещаем автоматическую установку через CI/CD.
- [Новая структура делает legacy несовместимым] → единый rollback книги/скрипта/образа и сохранение новых данных; запрет одного лишь отката Docker-тега.

## Migration Plan

1. Зафиксировать эталон ИФТ и рабочую конфигурацию read-only; составить структурный diff и карту соответствий. До любых production-записей получить готовность владельца с синхронизацией данных.
2. На копии текущего ПРОМ отрепетировать миграцию и восстановление; выполнить целевые проверки сохранности и все применимые Python/Node-тесты. Утвердить допустимый manifest изменений без изменения пользовательских финансовых полей.
3. Подготовить production-кандидат main, Compose и версию Apps Script. Проверить commit/tag, journal permissions и эффективные настройки без вывода token.
4. Остановить записи ПРОМ, сделать финальный нативный backup и экспорт скрипта, сверить source fingerprint и применить план к исходной книге. При изменении источника перепланировать до записи.
5. Установить и проверить Apps Script, validations, формулы, индексы, диаграммы, точные исходные поля и архивы. Не запускать saveMonthlyReport для smoke-test с очисткой.
6. После ready/open выпустить v-тег через существующий CI/CD, проверить workflow и один production polling, /version, аналитические и справочные чтения. До успешного открытия старый legacy-контейнер остаётся остановленным.
7. Передать владельцу ручную приёмку. Зафиксировать результат, фактические версии, backup и маршрут восстановления; не считать один deploy success полной приёмкой.

## Уточнение владельца — 2026-11-15

Владелец отменил дальнейшие репетиции/резервирование и поручил немедленный перенос структуры и выпуск ПРОМ. Собственные резервные копии у владельца есть; синхронизацию данных он выполнит после переноса. Старые требования дождаться синхронизации и установки Apps Script не применяются: макрос владелец устанавливает самостоятельно из data/macros.gs. Выпуск использует явное отложенное подтверждение установки, без фиктивного JSON proof. ИФТ не меняется.
