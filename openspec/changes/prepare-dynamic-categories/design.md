# Design

## Context

См. proposal.md и четыре delta-spec в specs/. Категории уже читаются из таблицы, но формулы используют текстовые критерии, архиватор — B9:B22, аналитика бота — четыре фиксированных названия. В операциях нет ID. Прошлые месяцы содержат агрегаты и снимки аналитики; восстановить удалённые исходные операции из этих данных нельзя.

Ниже — предлагаемые технические решения первого этапа. Подтверждённые владельцем правила жизненного цикла отражены в specs/category-lifecycle/spec.md. Публичные кнопки управления справочником будут отдельным изменением.

## Goals / Non-Goals

**Goals:** единый контракт справочника, независимая категория операции, динамические представления, ручное редактирование операций в Sheets, проверяемая миграция; внутренние операции готовы к будущему диалогу бота.

**Non-Goals:** новая БД, полная переделка bot.py, редактор всех операций в Telegram, восстановление отсутствующей построчной истории, автоматический деплой, миграция рабочей таблицы по одному лишь разрешению на разработку.

## Decisions

### 1. Версионированный справочник и постоянные ID

В пределах каждой таблицы создать служебные реестры:
- категории: category_id, type, name, active, deactivated_period;
- подкатегории: subcategory_id, current_category_id, name, active;
- исторические связи: category_id, subcategory_id, допустимые старые названия для миграции;
- метаданные: schema_version, taxonomy_revision, migration_state и состояние незавершённой операции.

ID — непрозрачные UUID, никогда не переиспользуются. У категории одно отображаемое название в пределах типа; у подкатегории — одно в пределах текущей категории. Коллизии проверяются с нормализацией пробелов и регистра; одинаковые подкатегории разных категорий допустимы и имеют разные ID. Перенос с конфликтом имени отклоняется, не объединяет историю.

Лист «Категории» остаётся читаемым представлением реестров и источником вариантов через служебные диапазоны. Реестры и ID защищены от случайного редактирования, но защита не объявляется запретом владельцу таблицы обходить её. Ручное изменение справочника не поддерживается; обнаруженное нарушение структуры блокирует запись до восстановления. В первом этапе публичного редактора ещё нет.

Альтернатива — продолжать использовать названия как ключи — делает глобальное переименование и исторический перенос неоднозначными. Отдельная серверная БД пока не нужна.

### 2. Операции сохраняют собственную категорию

Оставить A:F без перестановки. Добавить служебные category_id, subcategory_id, transaction_id, validation_state и нормализованную дату расчёта; поля определять по заголовкам, не зашивать их позиции в парсеры. ID хранятся как значения, не как формула поиска текущего родителя.

Для новой операции родитель берётся из текущего справочника. Для старой — из самой операции. Изменение суммы/даты/комментария не трогает связи, даже если подкатегория уже перенесена или деактивирована. Явное изменение B/C пользователем означает переклассификацию этой операции на активную допустимую пару; данные старых архивов автоматически не пересчитываются.

Переименование обновляет видимые названия по ID в текущих операциях и сохранённых отчётах, но не переносит суммы. Удаление — деактивация; период деактивации берётся из выбранного отчётного периода D1:D2, фиксируется и показывается будущим диалогом подтверждения. Это поддерживает текущий ручной процесс закрытия месяца.

Дата A сохраняет существующий контракт бота RAW; служебная дата принимает и настоящую дату Sheets, и поддерживаемый текст ДД.ММ.ГГГГ / YYYY-MM-DD. Месячные формулы используют нормализованную дату, не неявное сравнение текста с числом. Нераспознанное значение видно как ошибка, не нулевой расход.

### 3. Два пути ввода и обязательная сверка

Ручной ввод остаётся в A:F. Выпадающие списки строятся из активного справочника, список подкатегорий зависит от выбранной категории. При смене категории несовместимая подкатегория требует нового выбора. Историческая пара остаётся допустимой для неизменённых B/C старой строки, но не предлагается новым строкам.

Bound Apps Script обрабатывает пользовательские правки диапазона целиком: одиночный ввод, вставку нескольких строк и очистку. Служебный снимок по transaction_id позволяет отличить изменение B/C от изменения остальных полей. Для новой строки назначается ID; вставленный дублирующийся ID считается конфликтом. Сортировка поддерживается по целым строкам вместе со служебными полями; частичная сортировка отдельных колонок не является поддерживаемой операцией и проверяется при сверке.

Бот записывает A:F и ID одним запросом и не ждёт onEdit: API-записи не запускают edit-триггер. Перед чтением аналитики и архивацией выполняется полная сверка пользовательских полей, ID и снимков. Для Python-пути это идемпотентная сверка через адаптер Sheets; для макроса — та же таблица правил и общие тестовые примеры в Apps Script. Числа, скрывающие невалидные строки, не выдаются как полный отчёт. Ошибки и состояние «требуется синхронизация» отображаются рядом с аналитикой и пользователю бота.

Триггер ускоряет синхронизацию, но не является единственной гарантией: он может не отработать. Перед отчётом проверяется актуальность версии и состояния данных. Наборы контрактных примеров одинаковы для Python и Apps Script, чтобы две реализации не расходились.

Основание: [Apps Script triggers](https://developers.google.com/apps-script/guides/triggers): скриптовые/API-записи не запускают edit-триггеры; у простых триггеров есть ограничения выполнения.

### 4. Вычисления остаются в Sheets, представления генерируются

Не переносить бизнес-расчёт только в Python: пользователь продолжает работать в таблице. Генератор строит формулы месячной сводки по category_id и детализации по паре category_id/subcategory_id. Общие доходы, расходы и B5 сохраняют смысл; D1:D2 остаются ручным выбором периода.

Сохранить компактную сводку с привычными метками. Подкатегории хранить в отдельной генерируемой длинной таблице: category_id, subcategory_id, актуальные подписи, сумма, период. Это устраняет ручное размещение отдельных блоков G:H/J:K. Бот читает этот контракт и формирует динамический выбор по ID с разбиением на страницы при необходимости; индексы старого массива не используются как идентичность.

Представления обновляются из реестра идемпотентно. В отчётах остаются активные категории и исторические связи с операциями выбранного периода. Нули допустимы, ошибки исходных данных не превращаются в нули. Подкатегории учитываются вместе с категорией операции, поэтому перенос и одинаковые названия не смешивают суммы.

### 5. Архивные колонки идентифицируются, а не пересоздаются

Сохранить привычный широкий лист «Архив». В служебном реестре сопоставить category_id и колонку; новые категории добавляются справа. Исторические пустые значения новой колонки трактуются как отсутствие операций до создания, при миграции не переписывать существующие суммы ради внешнего вида.

После деактивации колонка остаётся: в период деактивации фактические расходы, после него — ноль. Поздняя ручная операция на неактивную категорию не должна незаметно приводить к расхождению между месячными расходами и сводкой: новая такая пара отклоняется; уже существующие конфликтные строки блокируют закрытие.

Месячные снимки остаются значениями. Их подписи и ячейки связываются с ID через служебный индекс снимка, чтобы будущий rename менял текст без пересчёта сумм. Для старых снимков индекс создаётся по подтверждённым названиям и контексту родительской категории. Слияние названий по догадке запрещено.

Макрос сохраняет сводку и снимок, сверяет их с отчётом периода, затем отдельно спрашивает подтверждение очистки. Отказ от замены существующего снимка завершает процесс без очистки. При операциях других периодов закрытие останавливается до удаления. Очистка не означает резервную копию исходных операций; отдельное изменение политики долговременного хранения не включено в этот этап.

### 6. Прикладные операции без новых пользовательских кнопок

Выделить небольшой модуль моделей и правил категорий и сервис подготовки/применения изменений. Telegram отвечает за диалог, сервис — за валидацию и план изменения, адаптер — за Sheets, Apps Script — за ручной ввод и закрытие месяца.

Каждая внутренняя операция принимает ID пользовательской таблицы, ожидаемую taxonomy_revision, request_id и подтверждение плана:
- create: новая идентичность, список подкатегорий, обновление проекций;
- rename: прежний ID, новые подписи во всех индексированных представлениях;
- move: изменение current_category_id и добавление исторической связи; операции и архивные суммы неизменны;
- deactivate: active=false и период; потомки категории исключаются из нового выбора.

При частичном сбое хранится план и выполненные шаги. Повтор с тем же request_id продолжает работу, не создаёт новую категорию. Пока изменение не завершено, новые записи и архивация блокируются, чтение не выдаёт несогласованные отчёты. Это не обещание общей транзакции Google Sheets.

### 7. Согласованность и границы конкурентности

В боте изменения одной пользовательской таблицы сериализуются. Apps Script использует document lock для собственных обработчиков; этот lock не защищает от Python и ручного редактирования ячеек. Не считать два механизма общей блокировкой.

Структурная миграция и применение изменения справочника выполняются в режиме обслуживания: остановить записи бота для таблицы, временно защитить пользовательский диапазон от ручных правок, проверить снимок/ревизию перед применением и после него. Владельцу сообщается запрет ручных изменений на это время. Внешнее изменение при сверке приводит к остановке, а не к перезаписи чужой правки. Полная конкурентная работа владельца, обходящего защиту, не гарантируется.

Обычный ручной ввод допускает промежуточно незаполненную строку; незавершённая классификация явно видна. Перед закрытием месяца приостановить новые записи и проверить неизменность исходного набора перед очисткой. Физическое удаление строки ботом дополнительно сверяет transaction_id и пользовательский снимок.

Основание: [LockService](https://developers.google.com/apps-script/reference/lock/lock-service) сериализует участвующие скрипты, а не произвольные обращения через Sheets API.

## Risks / Trade-offs

- [Это изменение формата данных, а не чистый рефакторинг] → версия схемы, совместная установка Python/Apps Script и отключение старого архиватора перед включением.
- [Исторические названия неоднозначны, например Самокаты/Whoosh] → предварительный отчёт и явная карта соответствий владельца; без неё live-миграция блокируется.
- [Старые архивы не содержат исходные операции] → сохранять агрегаты, не реконструировать недостающую историю; rename меняет подписи через индекс.
- [Переименование меняет много листов] → план по ID, проверка охвата всех снимков и восстановление по request_id; временно блокировать несогласованные отчёты.
- [Ручные правки обходят приложение] → сверка перед потреблением, защита служебных диапазонов, контрактные тесты Python/Apps Script; не обещать глобальные транзакции.
- [Генерируемый вид отличается от текущих блоков] → сохранить метки сводки, продемонстрировать копию таблицы и проверить все расчёты и диаграммы до установки.
- [Неизвестная семантика «Вклад»] → не включать её в доходы/расходы, сохранить исходные строки; не менять смысл этого типа в рамках миграции.
- [Работа требует нового доступа для установки Apps Script/защиты] → инструкции и перечень минимальных прав отдельно; не расширять доступ сервисного аккаунта автоматически.

## Migration Plan

1. Подготовить dry-run утилиту: только чтение, инвентаризация справочника, операций, формул, валидаций, архивных колонок/снимков. Выдать схему соответствий и конфликтов без личных сумм в логах.
2. Зафиксировать backup всей книги и версию Apps Script. С владельцем подтвердить конфликтные связи; никакого автоматического объединения разных названий.
3. На копии приостановить записи, присвоить ID, индексировать архивы, добавить служебные поля и валидации. Сохранить A:F, даты, суммы, типы и комментарии; повтор использует прежние ID.
4. Сгенерировать аналитику и динамический архиватор, установить edit-обработчик, проверить одиночный ввод, вставку диапазона и строки за прежней границей 155. Сверить доход, расход, остаток и каждую категорию/подкатегорию с независимым расчётом. Расхождения прежних формул оформить отдельным отчётом, не скрывать под «сохранением поведения».
5. На копии прогнать lifecycle-набор: create, rename, move, deactivate, сбои между шагами, повторный запуск. Подтвердить сохранение старых сумм и правила новых периодов.
6. Только после проверки и отдельного согласования установки повторить dry-run на рабочей таблице каждого пользователя, перейти в обслуживание, сверить исходный снимок, применить миграцию и установить согласованные версии. schema_version=2 и migration_state=ready публикуются последними.
7. При ошибке оставить режим обслуживания, сохранить диагностику, восстановить книгу и макрос из backup и только затем запустить прежнюю версию. Если после миграции появились новые операции, простой rollback запрещён: сначала отдельно сохранить и согласовать их перенос.

## Open Questions

Перед применением на рабочей таблице владелец подтверждает карту старых названий, требуемые права установщика и окно обслуживания. Эти данные не меняют выбранный подход; их отсутствие блокирует live-применение, а не заменяется предположениями. Точные расположения служебных листов и ширины колонок выбираются при реализации по описанным контрактам.
